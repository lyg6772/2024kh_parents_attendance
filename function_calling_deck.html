문제

왜 LLM에 '도구'를 붙이나

기존 SSR 화면

버튼 하나 = 기능 하나. 사용자가 정해진 UI를 눌러야만 동작합니다. 새 기능마다 라우터·컨트롤러·템플릿·JS를 다 손봐야 합니다.

도구 호출 방식

"오늘 김철수 추가해줘" 한마디 → LLM이 현재 출석 조회 → 변경 생성 → 승인 요청까지 스스로 조합합니다.

개발자는 '흐름'을 짜지 않고 '능력(도구)'만 선언합니다. 무엇을 어떤 순서로 쓸지는 LLM이 런타임에 판단합니다.

배경 — 30초

MCP는 무엇인가

LLM 앱과 외부 도구를 잇는 표준 프로토콜. 비유하자면 "AI계의 USB-C". 통합 코드를 M×N 에서 M+N 으로 줄입니다. 2024년 Anthropic 공개 → OpenAI·Google 채택 → 사실상 산업 표준.

도구를 JSON Schema로 표준화해서 — 누가 만든 도구든, 어떤 LLM 앱이든, 꽂으면 동작합니다.

구현

MCP의 '호스트' 역할을 인프로세스로

도구 레지스트리

Pydantic 모델에서 JSON Schema를 자동 생성. MCP 공식 SDK가 내부에서 하는 것과 같은 방식을 직접 씁니다.

ReAct 루프

LLM이 도구를 고르면 실행 → 결과를 대화에 다시 넣고 반복. 최대 5턴으로 무한루프를 막습니다.

자가수정

잘못된 인자는 예외로 죽이지 않고 에러를 대화에 되돌려줘 LLM이 스스로 고쳐 재시도하게 합니다.

쓰기 작업 승인

저장 같은 위험 작업은 실행 전 '현재값 vs 변경값' 미리보기 + 사용자 승인. human-in-the-loop 게이트.

프로바이더 Failover

Groq 한도 초과 시 Gemini로 자동 전환. 어댑터 구조라 모델 교체가 쉽습니다.

병렬 도구 호출

한 응답에 담긴 여러 도구 호출을 전부 처리합니다. 첫 개만 읽고 버리지 않습니다.

예시

"오늘 김철수 추가해줘" — 한 문장의 전 과정

  1. 턴 1
    READ

    현재 출석부터 확인. LLM이 스스로 "먼저 명단을 봐야겠다" 판단 → 이번 달 출석을 읽고 결과를 대화에 넣습니다.

  2. 턴 2
    WRITE

    김철수를 더해 저장 시도. LLM이 저장 도구를 고르지만, 위험 작업이라 엔진이 실행하지 않고 멈춥니다.

  3. 승인
    게이트

    미리보기 카드 표시. "명단에 김철수가 추가됩니다" — 현재값과 변경값을 보여주고 사용자 확인을 기다립니다.

  4. 완료
    저장

    사용자가 확인하면 그제야 DB에 저장 → "저장했습니다." (LLM을 다시 부르지 않고 끝)

SSR이면 명단 조회 화면 → 추가 폼 → 저장 확인을 각각 눌러야 하는 흐름을, 문장 하나로 엔진이 알아서 조합합니다.

판단

일부러 안 만든 것 — 그리고 그 이유

앱 ↔ 도구MCP가 표준화한 축. 저는 인프로세스 함수 호출로 해결 — 도구가 전부 제 코드라 프로토콜이 불필요.
앱 ↔ 모델MCP가 일부러 표준화하지 않은 축. 어댑터 + failover로 직접 처리.

넣지 않은 것

  • JSON-RPC 봉투
  • initialize 핸드셰이크
  • 버전·capability 협상
  • 페이지네이션
  • 도구 변경 알림

전부 '처음 만나는 상대와의 상호운용'을 위한 장치입니다. 제 시스템은 프론트 1 + 백엔드 1의 닫힌 구조라 상대가 없어 가치가 0 — 넣으면 오버헤드만 남습니다. "MCP 미달"이 아니라, 표준을 이해하고 규모에 맞게 취사선택한 것.

실전

분석하다 실제로 고친 것

2·2·3 → 1 LLM 호출 횟수 (단순 저장 / 저장+엑셀 / 연속 저장)

이미 받은 정보를 버리고 재구매하던 구조

모델이 한 응답에 여러 도구 호출을 줘도 첫 개만 읽고 버린 뒤, 그걸 되찾으려 승인 후 LLM을 또 불렀습니다. 프로바이더가 기본 제공하는 병렬 도구 호출을 살려 리팩토링 → 위 모든 경우가 LLM 호출 1회로 끝납니다.

조용히 죽던 버그를 잡음

에러 재시도 경로에서 짝 없는 메시지가 API 400으로 죽던 결함을 발견·수정. 문서나 기억이 아니라 git 히스토리를 근거로 판단했습니다.

다음

확장 경로

외부 클라이언트 연동이 필요해지면

핸들러를 공식 SDK(FastMCP)의 @tool로 감싸면 끝. 스키마는 이미 Pydantic이 만들고 있고, 프로토콜·에러코드는 SDK가 대신합니다. 갈아엎지 않고 얹는 구조.

규모·민감도가 커지면

자체 LLM + RAG로 도메인 지식 주입, 도구가 많아지면 2단계 라우팅, 데이터 외부 유출 차단. 어댑터 하나만 바꾸면 나머지 코드는 그대로입니다.
