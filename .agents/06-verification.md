# 6단계: 검증 + 실패 분류

## Role

구현된 코드를 검증하고, 실패 시 원인을 분류하여 적절한 단계로 라우팅한다.

## Input

- 5단계 산출물: 구현 코드
- 4단계 산출물: 테스트 코드 (보호 중)

## Process

### 1. 정적 검증

`.agents/context/codebase-conventions.md`의 "검증 커맨드" 섹션에 정의된 커맨드를 순서대로 실행한다:

1. 린트
2. 포맷
3. 타입 체크

### 2. 테스트 실행

`.agents/context/codebase-conventions.md`의 "검증 커맨드"에 정의된 테스트 커맨드를 실행한다.

### 2-1. e2e 실기동 검증 (테스트 전부 그린 후)

이것은 **실기동 1회**이고 회귀 자산이 아니다 — 레포에 e2e 스펙(playwright 등)이
있으면 그것은 4단계 전체 경로 축의 산출물이다. `TESTS_DIR` 안이면 LOCK 대상이고,
밖이면 LOCK 장치 없이 규범으로만 보호된다 (`04-test-generation.md` §1).
어느 쪽이든 실기동이 그 자산을 대체하지 않는다.

테스트가 못 잡는 배선 오류(라우터 미등록, 마이그레이션 누락, settings/DI 문제)를 잡는다.
런타임 표면이 없는 변경(문서, 순수 리팩터링으로 테스트가 전 경로 커버)은 생략하고 생략 사유를 기록한다.

1. **DB 스키마 변경이 포함된 기능이면 먼저 마이그레이션 정합성 체크** — dev 모드
   기동이 마이그레이션 없이 스키마를 자동 생성하는 스택(예: SQLAlchemy `create_all`)은
   마이그레이션 누락을 가리므로, 임시 DB에 **마이그레이션 적용만으로** 스키마가
   구성되는지 확인한다 (커맨드는 conventions "e2e 실기동" 참조 — 예: alembic이면
   `alembic upgrade head`).
   **롤백 왕복**: 이번 변경이 down-migration을 포함하면 적용 → 롤백 1단계 → 재적용
   왕복을 1회 돌려 롤백이 깨지지 않는지 확인한다 (예: `upgrade head → downgrade -1 →
   upgrade head`) — expand-contract가 롤백 필요를 줄이지만 제거하진 않고, 깨진
   롤백은 배포 후 롤백 시점에야 드러난다.
   불가역(데이터 소실) downgrade면 왕복 대신 그 사실을 산출물에 명시한다 (파괴적 변경은
   3단계 게이트에서 이미 승인됨)
2. `.agents/context/codebase-conventions.md`의 "검증 커맨드" e2e 섹션대로 앱을 실기동한다
3. 이번 변경이 건드린 플로우를 실제 요청으로 1회 이상 구동한다 (성공 경로 + 에러 경로 1개)
4. 응답 상태코드/본문이 설계 문서의 스펙과 일치하는지 확인 후 앱을 종료한다
5. 설계 §3-2에 관측이 있으면, **에러 경로 실행 시** 정의된 로그/지표가 실제로
   방출되는지 확인한다 — 조용한 실패(로그 없는 500)는 프로덕션에서 안 보인다.
   관측 설계가 없으면 이 단계 생략.

실패 시: 배선 문제 → 5단계. 스키마/마이그레이션 문제 → 원인 분류표에 따라 라우팅.

### 2-2. 신규 코드 커버리지 측정 (테스트 그린 후)

4단계 뮤테이션은 LOCK 시점 **테스트 그물의 구멍**을 봤다. 이건 5단계 구현이 추가한
분기(방어적 if, 에러 처리)가 **실제로 실행되는지**를 본다 — 아무 테스트도 안 밟는
분기는 검증 안 된 코드다. conventions "검증 커맨드"의 커버리지 옵션으로 이번 변경의
신규/수정 파일 대상 브랜치 커버리지를 측정한다 (커버리지 도구가 설정돼 있지 않으면
산출물에 "N/A - 커버리지 미설정" 1줄).

- 밟지 않은 신규 분기 → 각각 **사유 1줄** (테스트 불가 / 방어적 unreachable / 누락).
  "누락"이면 테스트 품질 문제 → 사람 보고 후 4단계 재개방 (아래 라우팅표).
- 임의 % 게이트를 세우지 않는다 (숫자 발명 금지) — 미커버 분기의 사유가 판정 기준.

### 3. 실패 시 원인 분류

| 실패 유형 | 원인 | 라우팅 |
|-----------|------|--------|
| 린트 에러 | 코드 스타일/import 문제 | → 자동 수정 (conventions의 lint fix 커맨드) 후 재검증 |
| 타입 에러 | 타입 불일치 | → 5단계: 구현 코드 수정 |
| 테스트 실패 — assertion | 구현이 스펙을 충족 못 함 | → 5단계: 구현 코드 수정 (테스트 수정 X) |
| 테스트 실패 — import/syntax | 구현 코드 구조 문제 | → 5단계: 구현 코드 수정 |
| 테스트 실패 — fixture | 테스트 인프라 문제 | → 사람에게 보고 |
| 테스트 자체 오류 의심 | 테스트가 설계를 잘못 반영 | → 사람에게 보고, 승인 후 4단계 수정 |
| 기존 테스트 깨짐 | 구현이 기존 코드에 영향 (회귀) | → 5단계: 기존 코드 영향 수정 (기존 테스트 수정 X) |
| 기존 테스트 깨짐 — 설계가 의도한 동작 변경 | 그 테스트가 옛 동작을 검증 (0단계 베이스라인·2단계 영향맵에 "의도된 변경"으로 표시됨) | → 사람 보고, 승인 후 4단계에서 기존 테스트 갱신 (`TEST_LOCK_OVERRIDE=1`, 결정 로그). 설계 문서 대조로 회귀와 구분 — 구현으로 phantom 회귀 좇지 않는다 |
| e2e 실패 — 배선 | 라우터 미등록, DI/설정 문제 | → 5단계: 배선 수정 |
| e2e 실패 — 마이그레이션/스키마 | 마이그레이션 누락·오류 | → 5단계: 마이그레이션 수정. 스키마 설계 자체 결함이면 사람 확인 후 3단계 |

### 4. 재시도 정책

- 린트 에러: 자동 수정 1회 시도
- 타입/테스트 에러: 5단계로 돌아가 수정 후 재검증
- **같은 원인으로 2회 연속 실패 → 3회째는 상위 모델로 승급**: 현재 세션이 직접
  세 번째 수정을 시도하지 않고, **fresh-context 서브에이전트(model: fable,
  effort: high)**에게 5단계 재실행을 위임한다 — 같은 원인 반복 = 어려운 문제라는
  증거가 이미 쌓인 유일한 자리라 최상위 모델 투입이 데이터로 정당화된다.
  커맨드의 고정 모델(sonnet)을 우회하는 유일한 경로가 명시적 model 지정
  서브에이전트다. 입력: 설계 문서 + 실패 테스트 출력 + 앞선
  두 시도의 요약 (단, 앞선 가설은 참고일 뿐 신뢰하지 말고 진단부터 다시 하라고
  명시). 승급 사실을 결정 로그에 기록한다.
- **3회 연속 동일 실패** (승급 시도 포함): 중단하고 사람에게 보고
- 7단계 REFACTOR로 재진입한 경우 실패 카운터는 리셋한다 (새 사이클). 전체 상한은 7단계의 재리뷰 2회 캡이 담당한다

### 5. 3회 연속 실패 시 보고 형식

```markdown
## 검증 실패 보고

### 실패 내용
[에러 메시지]

### 시도한 수정
1. [1차 시도: 무엇을 어떻게 수정했는지]
2. [2차 시도: 무엇을 어떻게 수정했는지]
3. [3차 시도: 무엇을 어떻게 수정했는지]

### 원인 분석
[왜 해결이 안 되는지]

### 선택지
1. [방안 A]
2. [방안 B]
```

## Output 템플릿

```markdown
## [6단계] 검증 산출물

### 입력
- 5단계 산출물: [구현 파일 목록]
- 4단계 산출물: [테스트 파일 목록]
- 누락 입력: [없으면 "없음"]

### 검증 결과
| 검증 항목 | 결과 | 비고 |
|-----------|------|------|
| 린트 | PASS/FAIL | [에러 시 내용] |
| 포맷 | PASS/FAIL | |
| 타입 체크 | PASS/FAIL | [에러 시 내용] |
| 테스트 | PASS/FAIL | [N passed, M failed] |
| 기존 테스트 | 영향 없음/깨짐 | [깨진 테스트 목록] |
| e2e 실기동 | PASS/FAIL/생략 | [구동한 플로우, 생략 시 사유] |
| 관측 방출 (에러 경로) | PASS/FAIL/N/A | [설계 §3-2 항목 방출 확인 / 관측 설계 없음] |
| 마이그레이션 롤백 왕복 | PASS/FAIL/생략 | [해당 없음/불가역-사유] |
| 신규 코드 커버리지 | 측정치/미설정 | [미커버 신규 분기 + 사유] |

### 구현 요약 (사람을 위한 설명)
- **무엇을 만들었는지**: [기능 설명 1~3줄]
- **어떤 구조인지**: [파일 구조, 레이어, 데이터 흐름]
- **핵심 결정 요약**: [왜 이렇게 만들었는지, 주요 트레이드오프]
- **확장 방법**: [나중에 기능을 추가하려면 어디를 건드리면 되는지]

### 종료 조건
- [ ] 린트 통과
- [ ] 타입 체크 통과
- [ ] 모든 테스트 통과
- [ ] 기존 테스트 영향 없음
- [ ] e2e 실기동 통과 (생략 시 사유 기록)
- [ ] 설계 §3-2 관측이 있으면 에러 경로에서 방출 확인 (없으면 N/A)
- [ ] 신규 코드 커버리지를 측정했다 (미커버 분기는 사유 기록, 도구 미설정이면 N/A)
- [ ] 마이그레이션 있으면 롤백 왕복 통과 (불가역이면 사유 명시, 해당 없으면 생략)
- [ ] 구현 요약이 사람이 읽고 이해할 수 있는 수준이다

### 실패 시
- [실패 유형] → [라우팅 대상]
```

## Rules

- 테스트 코드를 수정하지 않는다 (보호 중). 테스트 실패 = 구현이 틀린 것이다.
- 린트 자동 수정 외에는 검증 단계에서 코드를 직접 수정하지 않는다. 수정이 필요하면 5단계로 돌아간다.
- 3회 연속 실패하면 반드시 멈추고 사람에게 보고한다. 무한 루프를 돌지 않는다.
- 기존 테스트가 깨지면 기존 테스트를 수정하지 않고 구현 코드를 수정한다.
- 테스트가 객관적으로 잘못된 경우, 사람에게 보고하고 승인받아 4단계에서 수정한다.
- **6단계 통과 후 7단계(독립 리뷰)로 넘어간다.** 테스트 보호는 7단계 완료 시 해제된다.
- **구현 요약 필수**: 사람이 코드를 읽지 않아도 무엇이 어떻게 만들어졌는지 이해할 수 있도록 작성한다.
- **결정 로그**: 이 단계 완료 시 검증 결과, 구현 요약, "현재 상태: 6단계 통과, 7단계 리뷰 대기"를 결정 로그에 append한다. 결정 로그 최종화("현재 상태: 완료")는 7단계 통과 시점에 한다.
