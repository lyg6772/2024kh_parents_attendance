# 2단계: 기능 추출 & 영향 맵

## Role

요구사항 명세에서 구체적인 기능 목록을 추출하고, 각 기능이 코드베이스에 미치는 영향을 매핑한다.

## Input

- 1단계 산출물: 요구사항 명세
- 0단계 산출물: 코드베이스 컨텍스트 + 재활용 목록

## Process

### 1. 기능 목록 추출

요구사항에서 구현해야 할 기능을 추출한다:

- 각 기능의 이름과 설명
- 기능 간 의존관계
- 구현 순서 (의존관계 기반)

### 2. 재활용 매핑

각 기능에 대해 0단계의 재활용 목록을 참조하여:

- 기존 코드로 해결 가능한 부분 표시
- 기존 코드를 확장해서 해결할 부분 표시
- 새로 만들어야 할 부분만 남김

### 3. 영향 맵 작성

각 기능별로 생성/수정할 파일을 정리한다.

### 4. 불확실한 점 확인

기능 범위가 불확실하면 사람에게 질문한다.

### 5. 영향 맵 독립 검증 (필수)

영향 맵 확정 전, **작성에 관여하지 않은 fresh-context 에이전트(상위 모델)**가
영향 맵을 검증한다. 여기서 놓친 수정 파일은 설계·테스트·구현·리뷰 전체로 전파되는
최상류 결함이라 가장 비싸다.

검증 관점 (코드베이스를 직접 열어 확인, 추측 금지):
- **누락된 수정 파일**: 진입점 등록(라우터 등), 모듈 export, 공용 테스트 픽스처
  (예: `conftest.py`), 마이그레이션, 설정 — 신규 파일이 실제로 연결되려면 건드려야
  하는 기존 파일이 다 있는가
- **숨은 커플링**: 영향 맵의 파일을 import하거나 그 동작에 의존하는 기존 코드가
  영향 맵 밖에 있는가 — `.agents/context/codebase-conventions.md`의 "숨은 결합"
  레지스트리를 먼저 순회한 뒤
  grep으로 실제 확인. **새로 발견한 간접 결합은 레지스트리에 append** (자산화 —
  다음 기능부터 재발굴 비용 제거)
- **성능 함정**: 기능 목록에 목록 조회/관계 로딩이 있으면 N+1·인덱스 필요 여부
- **기존 테스트 영향**: 수정할 파일을 검증하는 기존 테스트가 깨질 것인가 —
  깨진다면 설계가 그 동작을 **의도적으로 바꾸는지(→ 4단계 갱신 대상, 사람 승인)**
  아니면 **회귀인지(→ 구현으로 방지)** 구분해 표시한다 (0단계 베이스라인 대조).
  이 구분이 없으면 6단계가 의도된 변경을 phantom 회귀로 오분류한다
- **정책 모순 (기획 vs 기존 정책)**: 이번 요구사항이 코드에 이미 구현된 기존 정책·
  불변식과 **동시에 성립 못 하는가**. "기존 테스트 영향"(위)은 테스트가 지키는 것만
  잡지만, 이건 **테스트 없는 정책과의 충돌까지** 본다 — 관련 불변식을 grep으로 실코드
  확인(추측 금지). 발견 시 사람 질문으로 승격 — 신규 요구와 기존 정책 중 무엇이
  맞는지는 사람만 안다.

비평가 입력: 이 단계 산출물 + 0단계 산출물 경로 + (정책 모순 점검용) 1단계 요구사항
명세뿐 (대화 이력 금지) — 정책 모순은 파생된 기능 목록이 아니라 요구 의도(제약·수용
기준)와 기존 정책을 대조해야 드러난다.
지적은 이 단계 안에서 반영 후 확정하고, 산출물에 "N개 반영" 또는 "지적 없음"으로 기록한다.

**소기능 통합 (토큰 티어링)**: 영향 파일이 3개 이하인 소기능은 1단계 완결성
비평가(01 §2-1)와 이 검증을 **비평가 1명**이 겸할 수 있다 (관점 목록은 양쪽 모두
순회). 통합 실행 시 결정 로그에 "비평가 통합 실행" 1줄 기록.
**단일 세션(/feature-dev) 실행에서만 적용** — 단계별 실행(/plan → /analyze)에서는
영향 파일 수를 1단계 시점에 알 수 없으므로 각 단계가 자기 비평가를 그대로 실행한다.

## Output 템플릿

```markdown

### 입력
- 1단계 산출물: [참조 여부]
- 0단계 산출물: [참조 여부]
- 누락 입력: [없으면 "없음"]

### 기능 목록
| # | 기능 | 설명 | 의존 | 재활용 | 신규 |
|---|------|------|------|--------|------|
| 1 | [이름] | [설명] | [의존 기능] | [기존 코드에서 재활용] | [새로 만들 것] |

### 구현 순서
| 순서 | 기능 | 이유 |
|------|------|------|
| 1 | [기능] | [왜 먼저인지] |

### 영향 맵

#### 생성할 파일
| 파일 경로 | 목적 |
|-----------|------|
| [경로] | [목적] |

#### 수정할 파일
| 파일 경로 | 변경 내용 |
|-----------|----------|
| [경로] | [변경 내용] |

#### 등록할 곳
| 위치 | 내용 |
|------|------|
| [파일 경로] | [등록 내용] |

### 영향 맵 검증 (§5)
- [지적 N개 반영: 목록 / 지적 없음]

### 종료 조건
- [ ] 모든 기능이 요구사항 명세에서 추출되었다 (임의 추가 없음)
- [ ] 재활용 매핑이 완료되었다
- [ ] 영향 맵에 생성/수정/등록 파일이 모두 포함되었다
- [ ] 독립 검증(§5)이 완료되고 지적이 반영되었다
- [ ] 정책 모순(기획 vs 기존 정책)을 점검했다 (충돌 시 사람 질문)

### 실패 시
- 기능 범위 불확실 → 사람에게 질문
- 기존 코드와 충돌 가능성 → 사람에게 보고
```

## Rules

- 요구사항에 있는 기능만 추출한다. 임의로 기능을 추가하지 않는다.
- 재활용 가능한 코드가 있으면 반드시 매핑한다. 중복 코드를 만들지 않는다.
- 영향 맵에서 기존 파일 수정을 누락하지 않는다. 특히 라우터 등록, 모델 export, 테스트 픽스처.
- 영향 맵은 독립 검증(§5) 없이 확정하지 않는다. 비평가는 코드베이스를 직접 열어 확인한다.
- 불확실한 범위는 추측하지 말고 사람에게 질문한다.
- **결정 로그**: 이 단계 완료 시 기능 목록, 구현 순서, 재활용 매핑을 결정 로그에 append한다.
