# 1단계: 기획 분석

## Role

유저의 요구사항을 분석하여 구조화된 요구사항 명세를 작성한다.

## Input

- 유저의 기능 요구사항 — 다음 중 어떤 형태든:
  - 대화로 전달된 자연어
  - **기획 문서 파일** (markdown, PDF, 노션 export 등 — 경로가 주어지면 전체를 읽는다)
- 0단계 산출물: 코드베이스 컨텍스트

## Process

### 1. 요구사항 추출

기획 문서가 파일로 주어지면 먼저 전체를 읽는다. 유저의 요구사항(대화 + 문서)에서 다음을 추출한다:

- 기능 요구사항 (무엇을 해야 하는가)
- 제약조건 (기술적, 비즈니스적 제한)
- 비기능 요구사항 (성능, 보안 등 — 유저가 언급한 것만)

### 2. 모호한 점 확인

다음에 해당하면 반드시 사람에게 질문한다:

- 해석이 2가지 이상 가능한 요구사항
- 범위가 불명확한 요구사항
- 기존 코드와 충돌 가능성이 있는 요구사항

### 2-1. 완결성 비평가 (독립 에이전트, 필수)

명세 초안 작성 후, **작성에 관여하지 않은 fresh-context 에이전트(상위 모델)**에게
초안 + 0단계 컨텍스트만 주고 **"이 명세가 정하지 않은 것" 목록**을 뽑게 한다.
모호함 검출(§2)은 쓰인 것의 해석 문제고, 이건 **안 쓰인 것**을 찾는 문제다 —
여기서 놓친 누락은 설계 초안 전부에 유전되므로 상류에서 차단한다.

점검 방법 — **힘(force) 분류 고정 순회** (완전성을 모델 천재성이 아니라 구조로 —
뮤테이션 연산자·분기 taxonomy와 같은 처방. 힘 = 어느 서비스에나 작용하는 보편
실패 클래스이고, 괄호는 이해 보조용 앵커 예시일 뿐이다 — 각 힘을 **이 기능**에
내려 인스턴스를 스스로 도출하라. 도메인 특화 렌즈는 커널이 아니라 타깃 레포
도메인 스킬 소유).

**원리**: 이 목록은 결정의 **부재**만 잡는다 — 통제/기능 도입을 요구하지 않는다.
"불필요 (근거)"도 동등한 정답이며 가정 표 1줄로 남긴다 (범위 준수 — 요구에 없는
것을 임의 추가하지 않는다). 힘이 작용하는 표면 자체가 없으면 "해당 없음 - 이유" 1줄.

| 힘 | 이 기능에 작용하면 명세가 정했어야 하는 것 (앵커 예시) |
|---|---|
| 시간 | 만료·유효기간·시효·순서 의존 (토큰/캐시 만료, 오래된 레코드 처리) |
| 동시 | 동시 행위자·중복 제출·경쟁의 결과 (중복 요청 멱등성, 동시 수정 충돌) |
| 규모 | 양이 커질 때의 동작 (페이지네이션, 상한, 대량 입력) |
| 적대 | 반복·대량·자동화·악의 호출 시 무슨 일이 나는가 — 신뢰 경계 밖 표면이 있을 때만 (호출 상한/쿨다운의 존재와 기준 키, 비용 발생 동작(외부 호출·발송·무거운 연산·저장)의 한도, 제3자의 식별자·한도를 소모시켜 정상 사용자를 차단하는 경로). 상류=요구 누락을 잡는 자리 — 7단계 보안 렌즈의 하류=구현 결함과 층이 다르다 |
| 동일성 | 사용자 입력 식별자의 비교·중복 판정·집계 키가 정규화 규칙을 갖는가 (대소문자/공백/유니코드 이형 — 없으면 "같은 값인데 다른 레코드" 사고) |
| 실패 | 외부 의존·부분 실패 시의 상태와 사용자 경험 (에러 시 UX, 재시도, 복구 경로) |
| 수명 | 생성→변경→삭제→삭제 이후 (hard/soft 삭제, 삭제 후 재생성, 기존 데이터 마이그레이션) |
| 접근 | 누가 무엇을 할 수 있나의 경계 (권한/인가 경계 — 구현 보안이 아니라 요구 수준의 결정) |
| 증적 | 남겨야 하는 기록 (감사/로깅 요구) |

이 9개 밖에서 이 기능 특유의 힘이 보이면 **최대 2개까지** 추가하되 근거 1줄
(쿼터 채우기 금지). 신규 힘(적대·동일성, 2026-07-25)은 하네스 개선 루프대로
적중 데이터로 검증한다 — 기능 5~10개 누적 적중 0이면 강등 후보.

힘 순회와 별개로 **필요한 접근 결정**을 점검한다 (이 요구를 실현하는 방법이
2개 이상인 지점이 있는가 — 명세가 그중 무엇을 정했는가. 기술: 저장 위치·인프라·
외부 서비스·처리 방식. 로직: 동시성/정합성 전략·상태 모델·계산/집계 방식·권한
모델. 예: "파일 업로드"는 저장소와 업로드 방식이, "재고 차감"은 동시성 전략이
미결정. 안 정해진 결정은 3단계 §0-2 솔루션 접근 결정의 입력이 된다).

**두 번째 렌즈 — 모순 (쓰인 것끼리 어긋남)**: 위가 *안 쓰인 것*(허점)이라면,
이건 *쓰였는데 동시에 성립 못 하는 쌍*을 찾는 문제다. 홀리스틱하게 "충돌 쌍을
찾아라"가 아니라 **고정 4유형을 순회**한다 (홀리스틱 1회 스캔은 초안에 양쪽 문장이
다 있어도 놓친다 — recall은 구조가 나른다). 각 유형: 해당 쌍이 없으면 "해당 없음" 1줄:

1. **동일 개념 이중 정의** — 같은 개념(수치·기간·상한·상태명)이 2곳 이상에서
   정의되면 값·단위·조건을 대조한다
2. **흐름 종착 대조** — 각 흐름/시나리오의 종착 상태를 추출하고, 같은 트리거를
   다루는 서술끼리 종착이 일치하는지 대조한다
3. **규칙 ↔ 예외/수용 기준 대조** — 규칙 표의 각 행이 예외 표·수용 기준과
   어긋나지 않는가
4. **권한·상태 표 ↔ 흐름 대조** — 표가 허용하는 것과 흐름이 전제하는 것이 맞는가

허점과 다른 실패 유형이므로 **출력을 별도 섹션으로 분리**한다 — 한 렌즈가 다른
렌즈의 recall을 희석하지 않게. 발견한 모순 쌍은 사람 질문으로 승격한다 (어느 쪽이
맞는지는 사람만 안다). 모순은 설계가 충실히 구현해버리는 최상류 결함이다.

출력: 미결정 항목당 1줄 (무엇이 안 정해졌나 / 안 정하면 생기는 일).
각 항목은 **사람 질문으로 승격**하거나, 사소하면 근거와 함께 "가정" 표로 내리거나,
**접근 결정 유형이면 "3단계 §0-2로 이월"** 처리한다 (결정 주체가 설계 단계이므로).
조용히 버리지 않는다.

### 2-2. 충실도·커버리지 비평가 (기획서 대조 — shadow, warn-only)

§2-1이 초안 하나만 보고 *안 정한 것/모순*을 찾는다면, 이 렌즈는 **기획서 원본과
초안을 나란히 놓고** "초안이 기획서를 충실히 옮겼나"를 본다 — 전사(transcription)
과정의 **의미 왜곡(확신에 찬 오독)**과 누락을 잡는다. §2의 모호함 검출은 모델이
스스로 "헷갈린다"고 느껴야 발동하므로 **확신에 찬 오독**(안 헷갈린 채 한쪽으로
확정)에는 장님이다 — 두 문서 대조는 확신과 무관하게 불일치를 드러낸다.

**발동 조건:** 기획 문서 파일이 주어진 경우만(§Input). 순수 대화 입력이면 대조
대상이 없으므로 N/A로 건너뛰고 사유를 남긴다.

**입력:** 기획서 원문(전체) + 명세 초안. 초안 작성 세션과 **다른 모델**로 돌린다 —
같은 모델 계열은 같은 오독을 공유해 버그를 "①일치"로 흘려보낼 수 있다(가능하면
계열도 다르게). 초안의 *출처* 칸을 신뢰하지 않는다 — 오독은 출처 선택 자체를
틀리게 하므로, 기획서 span을 전체에서 **독립적으로** 찾는다.

**방법 — 구조적 열거(홀리스틱 "맞아?" 판단 금지):** 기획서의 명사(범위/단위)·
동사(행위자/대상/시점)·수량(경계/단위)을 뽑아 각각이 초안에 어떻게 안착했는지
항목별로 대조한다. 완전성을 모델 천재성이 아니라 구조가 나른다(§8-1·뮤테이션과
같은 원리).

**항목별 판정:**
- ① 일치.
- ② 기획서 명시인데 초안이 다름 → **불일치**. 예: 기획서 "사용자당 1회" ↔ 초안
  "주문당 1회".
- ③ 기획서 미결정인데 초안이 임의 확정 → **§2-1과 동일 triage**(사람 질문 승격 /
  가정 표로 / §0-2 이월). 사람 직행 아님 — 대부분 가정이다.
- 커버리지: 기획서 요소 중 초안 어디에도 안착 못 한 것 → **누락(drop)**.

**한계(정직 섹션 필수):** 기획서의 도형·와이어프레임·표 등 **비텍스트 요구는
텍스트 열거로 못 본다** — 소스에 그림/표가 있으면 사람에게 플래그한다. 저확신
항목은 "저확신"으로 표시한다. 깨끗한 ①일치 표가 무결을 뜻하지 않는다.

**shadow(warn-only) — 하네스 개선 루프 #2:** 이 장치는 경고만 낸다, 파이프라인을
막지 않는다(근거가 설계 추론이지 로그된 유출이 아니므로 shadow로 도입). ② 불일치를
잡을 때마다 결정 로그에 `장치 적중: 충실도` 1줄 기록(/doctor step 12 집계). 5~10
기능 동안 실제 ② 적중이 있으면 차단으로 승격, 없으면 삭제한다. ③·drop은 기존
triage로 흐르므로 shadow 여부와 무관하게 처리된다.

### 3. 추가 고려사항 검토 (비판적 사고)

요구사항을 수용하더라도 다음을 검토한다:

- 요구사항 외에 추가로 고려해야 할 점이 있는지 (보안, 에러 처리, 엣지 케이스 등)
- 나중에 되돌리기 어려운 결정이 포함되어 있는지
- 더 나은 접근 방법이 있는지

검토 결과 중요한 추가 고려사항이 있으면 산출물의 "추가 고려사항" 섹션에 기록하고 사람에게 논의를 제안한다. 사소한 것은 기록만 하고 진행한다.

### 4. 요구사항 명세 작성

확인된 내용을 구조화한다. **각 기능 요구사항에는 검증 가능한 수용 기준**(무엇이
관찰되면 충족인가)을 붙인다 — 수용 기준 없는 요구사항은 4단계에서 테스트로 옮길
근거가 없다. 기준은 코드가 아니라 관찰 가능한 결과로 쓴다 (예: "만료 토큰으로
호출하면 401"). 또한 요구에서 자연히 연상되지만 이번엔 **안 하는 것**(non-goal)을
명시한다 — 스코프 크립과 리뷰어 기대 어긋남을 막는다.

## Rules

- 유저가 말한 것만 요구사항에 포함한다. 확대 해석하지 않는다.
- 모든 요구사항에 출처(유저 원문의 어떤 부분)를 명시한다.
- 유저가 언급하지 않은 비기능 요구사항을 임의로 추가하지 않는다.
- 모호한 점은 추측하지 말고 사람에게 질문한다.
- 이전 단계(0단계) 산출물이 없으면 코드베이스를 직접 탐색하되, 누락 입력에 명시한다.
- **비판적 검토**: 요구사항을 그대로 수용하기 전에 추가 고려사항이 있는지 검토한다. 나중에 되돌리기 어려운 결정은 반드시 사람과 논의한다.
- **결정 로그**: 이 단계 완료 시 결정 로그에 요구사항 해석, 해소된 모호한 점, 핵심 가정을 append한다.
