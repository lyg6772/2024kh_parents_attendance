# 0단계: 코드베이스 탐색 & 영향 분석

## Role

기능 개발 전 현재 코드베이스를 탐색하여 재활용 가능한 자산과 영향받는 파일을 파악한다.

## Input

- 유저의 기능 요구사항 (자연어)

## Process

### 0. Compaction 복원 확인 (최우선)

`.agents/context/decisions/` 디렉토리를 확인한다:

- 진행 중인 피처의 결정 로그가 있으면 → 로그를 읽고 "현재 상태"에서 재개. 0단계를 다시 실행할 필요 없을 수 있다.
- 없으면 → 신규 피처. 아래 프로세스 진행.

### 1. 프로젝트 구조 스캔

**codegraph 감지 (우선)**: 레포 루트에 `.codegraph/`가 있으면 구조·호출 관계 파악은
codegraph 쿼리로 한다 (`codegraph explore "<심볼/질문>"` 또는 MCP `codegraph_explore`) —
스냅샷 문서와 달리 항상 실코드와 일치하고, grep+read 스윕보다 토큰이 싸다.
인덱스가 없으면 산출물에 **"codegraph 미사용 — `codegraph init` 권장"** 1줄을 남기고
아래 수동 스캔으로 진행한다 (인덱스 생성은 사람 결정; 템플릿 레포가 아닌
파생 프로젝트에서 만드는 것).

수동 스캔 시 다음을 읽는다:

- 레포 루트의 top-level 디렉토리 목록 (레이아웃을 가정하지 않는다 — `app/` 고정이 아닐 수 있음)
- 위에서 확인한 주요 소스/테스트 디렉토리 전체 구조
- 의존성 매니페스트의 의존성 목록 (repo-profile `DEPS_MANIFEST` — 예: `pyproject.toml`, `package.json`)
- `.agents/context/codebase-conventions.md` 컨벤션 (규칙/패턴 — 구조는 실코드가 진실)

### 2. 요구사항 관련 기존 코드 탐색

요구사항과 관련된 기존 코드를 찾는다:

- 관련 모델, 스키마, 레포지토리, 엔드포인트
- 관련 테스트, 설정, 예외
- 유사한 기능이 이미 구현되어 있는지

### 3. 재활용 가능 자산 분류

기존 코드를 세 가지로 분류한다:

- **직접 재활용**: 그대로 import해서 쓸 수 있는 것
- **확장 재활용**: 상속/조합으로 활용할 수 있는 것
- **신규 필요**: 기존에 없어서 새로 만들어야 하는 것

### 4. 영향 범위 파악

이 기능이 건드릴 기존 파일 목록을 작성한다.

### 5. 부채 겹침 보고 (debt.md가 있을 때)

`.agents/context/debt.md`가 있으면 이번 영향 범위(§4)와 겹치는 항목을 산출물에
보고한다 — **report-only, 갚을지는 사람이 결정** (어차피 여는 영역이라 상환의
한계 리스크가 최소인 시점이라 알리는 것. 겹치지 않는 안정 영역의 부채는 건드리지
않는 게 기본 — team-policy § 리팩토링 정책). 원장의 우선순위는 기록 당시 기준이므로
이번 요구사항·정책 맥락에서 중요도가 달라졌으면 재평가해서 함께 보고한다
(예: 저순위였던 항목이 이번 기획으로 핵심 경로에 놓임 → 상향 제안).

### 6. 기존 동작 베이스라인 (기존 관찰 가능 동작을 바꾸는 기능만)

이번 변경이 기존 동작을 바꾸면(신규 추가만이면 N/A) 바꾸기 **전** 현재 동작을
기록한다 — 바꾼 뒤엔 "원래 뭐였는지"를 복원 못 한다. 바뀔 경로별로: 현재
입력→출력/부수효과 1줄 + 그 동작을 지키는 **기존 테스트가 있는지**. 기존 테스트가
그 동작을 검증하고 있으면 이번 변경으로 깨질 것인지 표시한다 — 2단계 영향 맵과
6단계 라우팅이 "의도된 변경"과 "회귀"를 구분하는 근거가 된다. 코드는 읽기만 한다
(테스트 작성·수정은 이 단계 아님).

## Output 템플릿

```markdown
## [0단계] 코드베이스 탐색 산출물

### 입력
- 요구사항: [유저 요구사항 요약]
- 누락 입력: 없음 (0단계는 첫 단계)

### 프로젝트 현재 상태 (계층 명칭은 레포 컨벤션 기준 — 예: 모델/엔드포인트/레포지토리)
- 기존 도메인 모델: [목록]
- 기존 진입점 (엔드포인트/핸들러 등): [목록]
- 기존 데이터 접근 계층 (레포지토리 등): [목록]
- 기존 테스트: [목록]

### 재활용 가능 자산

#### 직접 재활용 (그대로 사용)
| 파일 경로 | 재활용 대상 | 용도 |
|-----------|------------|------|
| [경로] | [클래스/함수] | [어디에 쓸 것인지] |

#### 확장 재활용 (상속/조합)
| 파일 경로 | 확장 대상 | 확장 방법 |
|-----------|----------|----------|
| [경로] | [클래스/함수] | [어떻게 확장] |

#### 신규 필요
| 대상 | 이유 |
|------|------|
| [무엇] | [기존에 없는 이유] |

### 영향받는 기존 파일
| 파일 경로 | 변경 내용 |
|-----------|----------|
| [경로] | [변경 내용] |

### 부채 겹침 (§5)
| 부채 항목 | 위치 | 원장 우선순위 | 이번 맥락 재평가 |
|-----------|------|--------------|-----------------|
| [원장 항목 요약 1줄] | [파일/모듈] | [원장 기재값] | [유지 / 상향·하향 제안 + 사유 1줄] |

(겹침 없으면 표 대신 "겹침 없음" 1줄, 원장 자체가 없으면 "debt.md 없음" 1줄)

### 기존 동작 베이스라인 (§6)
| 바뀌는 경로 | 현재 동작 (입력→출력/부수효과) | 지키는 기존 테스트 | 이번 변경으로 깨짐? |
|-----------|------------------------------|------------------|-------------------|
| [경로] | [1줄] | [테스트 경로 / 없음] | [의도된 변경 / 해당 없음] |

(신규 추가만이면 표 대신 "기존 동작 변경 없음" 1줄)

### 종료 조건
- [ ] 요구사항 관련 기존 코드를 모두 탐색했다
- [ ] 재활용 가능 자산을 분류했다
- [ ] 영향받는 파일 목록을 작성했다
- [ ] debt.md 겹침을 확인했다 (원장이 있을 때)
- [ ] 기존 동작을 바꾸면 베이스라인을 기록했다 (신규 추가만이면 해당 없음)

### 실패 시
- 프로젝트 구조 읽기 실패 → 사람에게 프로젝트 경로 확인 요청
- Compaction 복원 시 결정 로그와 현재 코드가 불일치 → 사람에게 확인
```

## Rules

- 코드를 읽기만 한다. 수정하지 않는다.
- 재활용 가능한 것이 있으면 반드시 테이블에 포함한다. "탐색했으나 없었다"는 구체적 근거와 함께 기록한다.
- 요구사항 범위 밖의 코드는 탐색하지 않는다.
- 불확실한 점이 있으면 사람에게 질문한다.
- **결정 로그**: 이 단계 완료 시 `.agents/context/decisions/{feature-name}.md`를 생성하고 탐색 결과와 핵심 판단을 기록한다.
- **Compaction 복원**: 기존 결정 로그가 있으면 먼저 읽고, 중복 탐색을 피한다.
