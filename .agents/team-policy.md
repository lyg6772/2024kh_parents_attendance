# Team Policy

팀 운영 규칙. 브랜치 전략, PR, 코드 리뷰, 핫픽스, 예외 처리.

## 브랜치 전략

| 브랜치 유형 | 네이밍 | 용도 |
|------------|--------|------|
| 기본 브랜치 (main/master — `scripts/default_branch.sh`로 해석) | — | 배포 가능 상태. 직접 push 금지 |
| `feat/<설명>` | `feat/user-auth` | 새 기능 개발 |
| `fix/<설명>` | `fix/login-validation` | 버그 수정 |
| `hotfix/<설명>` | `hotfix/crash-on-startup` | 긴급 수정 (프로덕션) |
| `refactor/<설명>` | `refactor/repository-pattern` | 리팩터링 — 파이프라인 밖, §리팩토링 정책 적용 (공유 코드 접촉 시 fix급 검증) |
| `docs/<설명>` | `docs/api-guide` | 문서만 변경. **파이프라인 밖** — 산출물/결정 로그 불요, process-audit는 게이트 조건 diff 침범만 검사 |
| `chore/<설명>` | `chore/ci-cache-tune` | 빌드·설정·하네스 변경. **파이프라인 밖** (docs와 동일 규칙) |

> **의존성 변경은 `chore/`가 아니라 `feat/`다.** 의존성 매니페스트를 건드리면
> `deps` 게이트가 켜지고, **파이프라인 밖 브랜치(`chore/`·`docs/`·`refactor/`)에서**
> 게이트 조건이 하나라도 켜지면 process-audit이 하드 레드를 낸다
> (`10-process-chain.sh` — *"use a feat/ branch and run the pipeline"*). 이건 버그가
> 아니라 규칙이다: 새 의존성은 사람 승인이 필요하고, 그 승인 기록이 사는 곳이
> 파이프라인의 결정 로그다. 파이프라인 밖에는 그 기록을 둘 자리가 없다. CVE
> 업그레이드처럼 코드 변경이 없는 경우도 마찬가지다 — 승인이 필요한 이유가 코드가
> 아니라 의존성이기 때문이다.
>
> **예외 하나: 하네스를 설치하는 PR.** 그 PR 은 의존성과 고위험 경로를 함께
> 건드리지만 아직 파이프라인이 없어 산출물을 만들 수 없다. 브랜치 이름이 아니라
> **diff 가 `.agents/workflow.md` 를 추가하는지로 자기 탐지**되어 면제된다
> (이름 규약이면 누구나 타이핑하는 우회가 된다). 파괴적 마이그레이션·공급망 검사는
> 그때도 그대로 돈다.

- 브랜치 이름은 영문 소문자 + 하이픈. 한글 금지.
- 하나의 브랜치 = 하나의 기능 또는 하나의 버그.

## 커밋 메시지

```
<type>: <summary>

<body (선택)>
```

| type | 용도 |
|------|------|
| `feat` | 새 기능 |
| `fix` | 버그 수정 |
| `refactor` | 동작 변경 없는 코드 개선 |
| `test` | 테스트 추가/수정 |
| `docs` | 문서 변경 |
| `chore` | 빌드, 설정, 의존성 변경 |

- summary는 한 줄, 50자 이내, 현재형 동사로 시작.
- 예: `feat: add user authentication endpoint`

### Provenance 트레일러 (에이전트 생성 커밋 필수)

AI가 만든 커밋은 본문 끝에 출처 트레일러를 남긴다 (SLSA/ISO 42001식 감사 추적 —
"어떤 모델이 어느 단계에서 만들었고 누가 승인했나"를 커밋 자체가 증언):

```
Pipeline-Stage: 5-implement          # 파이프라인 단계 (0~7, 해당 시)
Model: opus                          # 그 커밋을 만든 세션 모델
Approved-By: yglee                   # 게이트 승인이 걸린 커밋만 (설계 게이트, override)
Co-Authored-By: <agent> <email>
```

- `Approved-By`는 사람 승인이 실제로 있었던 커밋에만 — 없는데 쓰면 위조다.
- squash 머지 본문에 원 커밋 트레일러가 함께 보존된다.

## Pull Request

### PR 생성 규칙

- PR 제목: 커밋 메시지와 동일한 형식 (`<type>: <summary>`)
- PR 본문에 포함할 것:
  - **변경 요약**: 무엇을 왜 바꿨는지 1~3줄
  - **설계 산출물 링크**: 3단계 설계 문서 (설계 게이트 대상인 경우)
  - **테스트 결과**: 린트, 타입 체크, 테스트 통과 여부
  - **영향 범위**: 변경된 파일 목록과 영향받는 기존 기능

### 사람 게이트 (PR 승인)

풀 바이브 코딩 전제: 사람은 코드가 아니라 **산출물을 승인**한다. 코드 판정은
stage 7(cto-reviewer verdict)과 pr-review-gate가 담당한다 — 이걸 정직하게 인정하고,
사람 체크리스트를 사람이 실제로 판단 가능한 것으로 한정한다:

- [ ] 구현 요약(6단계)이 내가 요청한 것과 일치하는가
- [ ] "검증하지 못한 것"(7단계)의 리스크를 감수할 수 있는가
- [ ] 게이트 브리핑의 파괴적 변경·되돌리기 난이도를 이해했는가
- [ ] 가정 대장에 틀린 가정이 없는가
- [ ] 영향 범위(변경 파일 목록)가 요청 규모와 비례하는가 — 비례하지 않으면 질문

코드를 읽을 수 있는 팀원이 있으면 기존 코드 리뷰를 추가로 수행한다 (권장, 필수 아님).

### 머지 규칙

- 사람 게이트 승인 + CI 통과 후 머지. **머지 실행은 PR 단위의 명시 지시** —
  세션 중 앞선 머지 지시를 이후 PR에 대한 상시 승인으로 확대 해석하지 않는다.
- 머지 판단 전 **도착한 봇 리뷰를 확인**한다 (리뷰 등록은 PR 생성 후 통상
  ~5분 지연 — 그때까지 부재≠스킵). 지적은 유효/기각 분류 후 처리하고 기각은
  사유를 **해당 리뷰 코멘트에 회신**한다. 사후 도착분은 후속 PR로 처리한다
  (원천 하네스 레포의 실제 유출 사례에서 도출된 규칙).
- squash merge 기본. 커밋 히스토리를 깔끔하게 유지 (squash 메시지에 원 커밋 본문 전문 보존 — RAG/추적용).
- **branch protection 필수 설정** (레포 셋업 시 1회): 기본 브랜치에 required status checks
  (`quality`, `process-audit`) + PR 필수 + force-push/삭제 금지 + enforce admins.
  이게 없으면 아래 모든 게이트가 자문(advisory)으로 전락한다.
  팀 확장 시 업그레이드: required approving review + CODEOWNERS 리뷰 필수
  (사람 승인을 에이전트가 위조할 수 없는 곳에 앵커).
- **Dependabot alerts 필수 설정** (레포 셋업 시 1회, 파생 프로젝트 포함): 휴면 기간에도 CVE 경보가 유지된다. CI osv-scanner는 push/PR
  활동이 있어야만 돌고, scheduled workflow는 60일 비활성 시 GitHub가 자동
  비활성화하므로 대안이 못 된다. **version-update PR은 켜지 않는다** —
  `dependabot/*` 브랜치는 process-audit 브랜치 규약 밖이라 레드가 난다
  (켜려면 audit prefix 처리부터).

### 위험 수용 기록 (형식 — 레포별 실기록으로 작성)

통제 공백을 수용할 때는 아래 형식으로 **이 레포의 실기록**을 남긴다. 커널이
배포하는 것은 형식뿐이다 — moru-init 직후는 빈 상태가 정상이며, 남의 레포
기록을 상속하지 않는다 (위험 수용은 상속되지 않는다). 전형 사례: 플랜 제약으로
branch protection 불가 → 로컬 pre-push 게이트 + PR 경로 감사로 보상.

| 항목 | 내용 |
|------|------|
| **제약** | [무엇이 불가한가 + 확인 근거·일자] |
| **잔여 위험** | [무엇이 물리적으로 가능해지나] |
| **수용 근거** | [왜 수용 가능한가 — blast radius, 실통과 중인 보상 경로] |
| **보상 통제** | [공백을 대신 덮는 장치 목록] |
| **해제 조건** | [수용이 무효가 되는 조건 — 반드시 명시] |
| **재검토** | [주기 + 상기 장치 (예: `/doctor` step 11)] |
| **승인** | [사람, 일자] |

### Override 기록 (필수)

`TEST_LOCK_OVERRIDE=1`, `PR_REVIEW_SKIP=1`, `PR_REVIEW_ROUND_CONTINUE="<사유>"`,
`audit-exempt` 라벨을 쓸 때마다 결정 로그에 **`override 사용:`** 라인(무엇을, 왜)을 남긴다.
`PR_REVIEW_ROUND_CONTINUE` 는 리뷰 상한에 걸린 **한 라운드만** 승인하고(리뷰는 그대로 돈다)
**사람이 지시했을 때만** 쓴다 — 에이전트도 설정할 수 있으므로 자기 승인은 규범 위반이다.
비파이프라인 브랜치(chore/docs/refactor)는 결정 로그가 없을 수 있다 — 이미 있으면
(공유 코드 접촉 `refactor/` 등, §리팩토링 정책) 거기에 남기고, 없으면 override 사용 시
`.agents/context/decisions/<브랜치-슬러그>.md`를 만들어 `override 사용:` 1줄만
남긴다 — `/doctor` step 10 집계가 그대로 잡는다 (별도 원장 파일은 동시 브랜치
append 충돌 때문에 쓰지 않는다).
`PR_REVIEW_SKIP=1`은 **사람 전용** — 게이트가 `/dev/tty`에서 `SKIP` 직접 입력을
요구하므로 터미널 없는 에이전트 셸에서는 통과할 수 없다. CI process-audit이
LOCK 윈도우 override를 검사하고, `/doctor`가 사용 빈도를 집계한다 —
**override 빈도 증가가 품질 드리프트의 1차 경보다.**

`audit-exempt`의 효력 범위: **프로세스 검사**(산출물 체인, 형식)만 경고로
강등된다. **안전 핵심 검사** — LOCK 윈도우, 파괴적 마이그레이션, 게이트 우회
(비파이프라인 브랜치의 게이트 diff 포함), alembic head 분기 — 는 라벨과 무관하게
FAIL 유지. 안전 핵심을 통과시키는 유일한 길은 요구된 기록을 실제로 남기는 것이다.

## 하네스 개선 루프 (프롬프트 self-healing)

이 하네스는 특정 개인의 감각이 아니라 데이터로 진화한다. 코드에 적용하는 규율을
`.agents/` 프롬프트와 검증 장치에 똑같이 적용한다:

1. **근거 없는 변경 금지**: `.agents/`·`scripts/audit/`(그리고 플러그인 쪽 커맨드·에이전트)를 바꾸는
   PR은 본문에 근거를 인용한다 — `유출 경로:` 기록, `장치 적중` 데이터, 실제 사고
   중 하나. 감각·취향만으로 장치를 추가·강화하지 않는다 (일방향 래칫 방지 —
   리뷰가 찾아낸 "구멍" 목록은 반영할 백로그가 아니라 판단 재료다).
2. **신규 장치는 warn-only로 도입**: 새 검증 장치는 경고만 내는 shadow 모드로
   들어와 5~10 기능 동안 적중 데이터를 쌓고, 실제 잡은 게 있으면 차단으로 승격,
   없으면 삭제한다. **하드월은 예외이자 동결 목록** — 테스트 LOCK 윈도우, 파괴적
   마이그레이션, 게이트 우회, 에이전트 런타임 권한. 이 목록은 실제 사고 사례
   없이는 늘리지 않는다.
3. **텔레메트리 소비**: `/doctor` step 12가 유출 경로(렌즈별)·장치 적중(장치별)을
   집계한다. 유출이 몰린 렌즈 = 프롬프트 보강 후보, **돌았는데도** 적중 0 장치 =
   강등 후보 (모든 칸이 0인 행은 미계측이지 강등 근거가 아니다 — 구분은
   `PORTING.md` § 이식 절차 4번이 소유한다) — 판단 재료는 기계가 만들고, 채택은
   사람이 한다.

이 루프는 레포에 독립적이다 — 파생 레포에서도 동일하게 적용되며, 운영자가
바뀌어도 하네스가 같은 규칙으로 진화한다.

## 동시 개발 (여러 기능 병렬)

| 상황 | 규칙 |
|------|------|
| 같은 파일을 건드리는 두 기능 | 먼저 머지된 쪽이 우선. 나중 PR이 충돌 해결 책임 |
| `router.py` 등 공유 파일 충돌 | 충돌 해결 후 전체 테스트 재실행 필수 |
| 모델/스키마 변경 충돌 | **순차화가 규칙**: 동시에 스키마를 바꾸는 피처는 한 번에 하나만 진행 (먼저 머지될 쪽이 끝날 때까지 다른 쪽은 4단계 진입 보류). 코드 판단이 필요한 예외만 사람이 결정 |

## 핫픽스 경로

프로덕션 긴급 수정은 전체 파이프라인을 축소 적용한다:

```
핫픽스 요청
    │
    ▼
0. 코드베이스 탐색 (영향 범위만 빠르게 확인)
    │
    ▼
3. 최소 설계 (수정 내용 + 영향 범위만)
    │  → 🧑 승인 필수 (핫픽스는 항상 승인)
    ▼
4. 테스트 작성 (해당 버그 재현 테스트)
    │
    ▼
5. 수정 구현
    │
    ▼
6. 검증
    │
    ▼
7-축소. 긴급 리뷰 (verifier 1명)
    │
    ▼
PR 생성 → 체크(quality/process-audit) 통과 확인 → 즉시 머지 + 배포
```

**핫픽스도 기본 브랜치 직접 push 금지** — 긴급해도 PR을 경유한다 (체크는 몇 분,
process-audit 없이 기본 브랜치에 들어간 핫픽스는 가장 위험한 무감사 변경이다).
PR 생성부터 머지까지 몇 분 안에 끝나므로 긴급성과 충돌하지 않는다.

- 1, 2단계 생략 가능 (이미 문제가 명확하므로).
- **7-축소 (긴급 리뷰)**: 렌즈 finder 3명은 생략하되, `cto-reviewer`(verifier) 1명은
  fresh context로 diff + 최소 설계만 보고 리뷰한다. 프로덕션 직행 변경이 파이프라인에서
  제일 위험한데 리뷰를 전부 생략하는 건 모순이므로, 리뷰 없는 경로는 없다.
  verifier 판정 blocker → 사람에게 즉시 보고 (배포 여부는 사람이 결정).
- 재현 테스트 LOCK 규칙은 버그 수정 경로와 동일 (lock 커밋 필수, 검수·뮤테이션 생략 수용 포함).
- 핫픽스 후 회고: 근본 원인 분석 + 추가 테스트 보강 + **정식 7단계 리뷰**를 별도 `fix/` 브랜치로 진행.

## 버그 수정 경로

일반적인 버그 수정 (긴급하지 않은):

```
버그 리포트
    │
    ▼
0. 코드베이스 탐색 (원인 파악)
    │
    ▼
4. 버그 재현 테스트 작성
    │
    ▼
5. 수정 구현
    │
    ▼
6. 검증
    │
    ▼
7-축소. 리뷰 (verifier 1명)
```

- 1, 2, 3단계 생략 가능 (새 기능이 아니므로).
- 3단계를 생략하므로 4단계 입력은 설계 문서 대신 **버그 리포트 + 0단계 원인 분석**이다.
  4단계 산출물의 "누락 입력"에 "설계 문서 없음 (버그수정 경로)"를 명시한다.
- **재현 테스트도 LOCK한다** — feat와 동일하게 lock 마커를 커밋한다. CI 감사가
  하드 강제 중이다: fix/hotfix가 `tests/`를 건드렸는데 lock 커밋이 없으면 레드
  (`scripts/audit/20-test-lock.sh`, safety-core — audit-exempt 무효). 단
  **LOCK 전 독립 검수·뮤테이션 검증(04 §4·§4-1)은 feat 전용** — fix에서는
  생략을 명시적으로 수용한다 (2026-07-20: 재현 테스트 1개엔 뮤테이션이 거의
  항상 뚫려 스코프만 팽창. 방어는 7-축소 verifier + 유출 시 escaped-bug 루프로 재론).
- 설계 게이트 조건에 해당하면 (기존 동작 변경 등) 3단계 + 승인 추가.
- **7-축소**: 핫픽스와 동일 — finder 생략, `cto-reviewer` 1명이 fresh context로
  diff + 재현 테스트를 리뷰. 리뷰 없는 경로는 없다 (버그수정이 최다 빈도 변경 유형).

## 리팩토링 정책 (경계 · 매 PR · 주기)

**경계 (무엇이 리팩토링인가)**: 기존 테스트를 **수정 없이** 그린으로 유지하는
변경만 리팩토링이다 — 기존 스위트가 오라클이고, 새 테스트를 먼저 쓰지 않는다
(TDD는 동작을 추가할 때의 규율, 동작 보존의 규율은 기존 테스트다). 테스트를
고쳐야만 되는 변경은 리팩토링이 아니라 **동작 변경** — `refactor/`가 아니라
feat/fix로 파이프라인(설계 게이트부터)을 탄다.

**매 PR**: stage 7 체크리스트 #4(재사용)·#5(과잉 설계)가 diff 범위의 리팩토링
관점을 커버한다 (spec-일치 finder가 #5 겸임 — `07-review.md` §1-1). REFACTOR
verdict 루프 내내 테스트 LOCK 유지 = 리팩토링이 계약을 깨지 않음을 기계가 보증.

**주기 (누적 부채)**: diff 리뷰는 교차-기능 중복(rule of three)·모듈 비대·죽은
코드·컨벤션 드리프트를 구조적으로 못 본다 — 각 PR이 개별적으로는 정당하기 때문.
**기능 5~10개마다** (장치 적중 리뷰와 같은 주기, `/doctor` step 12와 동시)
**`/debt-audit` 커맨드로 실행한다** — 커맨드가 fresh-context 에이전트를 띄워
**전체 레포** 부채 감사를 수행한다 (선언이 아니라 도구 호출이 트리거).
렌즈는 코드와 문서 양쪽:

- **코드 부채**: 중복 구현 / ~200줄 초과 모듈(AGENTS.md 분리 규칙) / 죽은 코드 /
  컨벤션 드리프트
- **문서 부채** (하네스 문서 자신 — `.agents/`·`docs/`·커맨드): ① 죽은 참조
  (없는 파일·섹션을 가리키는 링크 — `/doctor` step 13이 기계 검사로 후보를 공급)
  ② 해소된 항목 잔존 (✅·취소선 항목은 "해소 — 1줄 + 커밋 링크"로 접고, 버전
  로그류 append 섹션은 최신 2개만 상세·이전은 1줄). **접기 제외**: `docs/adr/`
  (append-only), `.agents/context/decisions/`(영구 보존), `artifacts/`(수명
  정책 별도) — 이들은 접지 않는다 ③ **같은 규칙의 다중 풀텍스트
  서술** — 한 곳을 소스로, 나머지는 참조로 (근거 사례: 사전 승인 패턴 헤더가
  편집 한 번에 옛 버전으로 회귀해 문서 간 모순 발생) ④ 스테이지 파일이 ~300줄을
  넘으면 "매 실행에 필요한 지시" vs "예외 시에만 필요한 상세"의 분리 검토 —
  스테이지 파일은 매 실행 프롬프트라 비대 = 토큰 비용 + 지시 희석.
  분리의 1차 대상은 **산출물 템플릿**이다 (추론 대상이 아니라 그대로 찍히는
  스캐폴딩). 선례: `03-design.md` 의 템플릿이
  `03-design-output.md` 로 빠졌고, 판정 기준인 종료 조건은 지시 쪽에 남았다.
  게이트 전용 **지시**(best-of-4·Devil's Advocate)는 분리하지 않았다 — 게이트
  대상일 때 반드시 읽혀야 하는 절이라 한 홉 뒤로 보내면 "링크는 읽기를 보장하지
  않는다"에 걸린다. **되돌림 조건**: 형식 파일을 안 열어
  설계 산출물에서 절 누락이 실제 관측되면 — 그것이 이 분리가 산 위험이므로,
  템플릿을 지시 파일로 되돌리거나 종료 조건에 절별 확인을 추가한다

산출물은 `.agents/context/debt.md` 대장 (항목 / 위치 / 제안 / 우선순위) —
각 항목은 `refactor/` 브랜치 하나씩으로 처리하고 완료 시 대장에서 지운다.
동작 보존 리팩토링은 "방법+오라클(기존 테스트) 주어짐" 조건이므로 저비용 모델로
충분하다 (모델 티어링 원칙).

**refactor/ 차등**: 국소 리팩토링(공유 코드 무접촉)은 기존 테스트 + CI +
pr-review-gate로 충분. **공유 코드(base 클래스, `app/core/`, deps — repo-profile
`SHARED_CODE_RE`)를 건드리면** fix급 축소 검증을 요구한다: 06 검증 산출물(전체
테스트 + e2e) + 07-축소 리뷰(verifier 1명) + 결정 로그. CI 감사가 검사하되,
신규 장치이므로 하네스 개선 루프 #2대로 **shadow(warn-only)로 도입** — 적중
데이터가 쌓이면 차단으로 승격.

## 전역 결정 기록 (ADR + 현황판)

결정 로그는 **피처 단위**라 기능이 쌓이면 "우리 X를 왜 이렇게 하지?"가 피처명으로
흩어진 파일 더미가 된다. 전역 영향 결정은 `docs/adr/`로 승격해 도메인 관점으로
집적한다. 구조는 2층: **현황판**(`docs/adr/README.md` — 현재 유효한 결정만,
한눈에) + **ADR 파일**(append-only 이력 — 근거·탈락안·대체 경위).

- **규칙·형식·승격 대상·시점의 단일 소스는 `docs/adr/README.md`다** — 여기에
  다시 쓰지 않는다 (문서 부채 렌즈 ③).
- **백스톱** (이 문서 고유): 주기 부채 감사(`/debt-audit`)가 함께 검사한다 —
  ① 그 주기의 결정 로그 중 승격 누락 ② 현황판 ↔ ADR 정합 (채택 ADR은 전부
  현황판에, 대체된 ADR은 현황판에 없음, 현황판 행은 전부 실재 ADR 링크).

## 에이전트 런타임 권한 경계

파이프라인은 "작성되는 코드"를 통제한다 — 이 섹션은 "에이전트가 실행할 수 있는 것"을
통제한다 (Replit prod DB 삭제 사고 계열의 방어. 코드 리뷰로는 못 막는 층위):

| 규칙 | 내용 |
|------|------|
| **dev/prod 분리** | 에이전트 세션은 프로덕션 DB/인프라 크리덴셜을 보유하지 않는다. `.env`에 prod 크리덴셜 금지 |
| **prod는 read-only** | 운영 조사가 필요하면 read-only 크리덴셜만. 쓰기가 필요한 운영 작업은 **plan-only** — 에이전트가 커맨드를 제시하고 사람이 실행 |
| **파괴적 인프라 작업** | DB drop/truncate, 리소스 삭제, 시크릿 로테이션은 에이전트 단독 실행 금지 — 사람 승인 + 사람 실행 |
| **배포 권한** | 배포 트리거는 사람 (또는 사람이 승인한 CI). 에이전트가 직접 배포 커맨드를 실행하지 않는다 |

## 위험 차등 게이트 (risk-tiered)

모든 변경이 같은 위험이 아니다. 다음 **고위험 경로**는 설계 게이트가 항상 발동하고,
사전 승인 패턴을 **적용할 수 없다** (균일 게이트의 예외 상향):

- 인증/인가: 토큰/세션/권한 로직 — 경로 목록은 repo-profile `HIGH_RISK_PATH_RE`
  소유 (레포별 재생성, 예: FastAPI라면 `app/core/security.py`·`app/api/deps.py`)
- 개인정보(PII)·결제 관련 모델 필드/처리 로직
- 프로덕션 설정·시크릿 취급 코드 (동일 — `HIGH_RISK_PATH_RE`, 예: `app/core/config.py`)

감지 책임 분담: **경로 기반 항목**(security/deps/config)은 CI process-audit이 diff에서
감지해 사람 승인 기록을 요구한다. **PII·결제 로직은 경로로 기계 감지가 불가능**하므로
stage 3 설계 단계(judge + 게이트 판정)가 고위험 여부를 판정할 책임을 진다 —
설계 문서의 게이트 판정 체크리스트에 명시.
반대 방향도 유효: 저위험 반복 패턴(표준 CRUD)은 사전 승인 패턴으로 게이트를 낮춘다.

## 롤백 런북 (기본 브랜치 오염 시)

나쁜 머지가 기본 브랜치에 도달했을 때 — forward-fix(핫픽스)와 별개의 되돌리기 경로:

1. **판단**: 배포 전이면 revert로 충분. 배포 후 + DB 마이그레이션 포함이면 3번 먼저
2. **revert PR**: `git revert <머지 커밋>` → `fix/revert-<원래-기능>` 브랜치 → PR
   (직접 push 금지 — revert도 CI를 통과해야 한다). squash 머지
3. **마이그레이션이 적용된 경우**: 마이그레이션 롤백(예: `alembic downgrade -1`)은 **파괴적 마이그레이션이면
   데이터를 복구하지 못한다** — 게이트 브리핑의 "파괴적 변경" 기록을 먼저 확인하고,
   복구 불가면 사람이 백업 복원 여부를 결정 (에이전트 단독 결정 금지)
4. **기록**: revert PR의 결정 로그에 원인 + `유출 경로:` 기록 (escaped-bug 루프로 편입)

## 의존성 추가 정책

새 패키지 추가 시:

1. 3단계 설계에 의존성 추가 사유를 명시한다.
2. 사람 승인을 받는다 (설계 게이트 대상).
3. 의존성 매니페스트(repo-profile `DEPS_MANIFEST` — 예: `pyproject.toml`)에 추가할 때 버전 범위를 명시한다 (`>=X.Y.Z`).
4. 기존 패키지로 해결 가능한지 먼저 확인한다.

## 버그 유출 기록 (escaped-bug 되먹임)

`fix/`·`hotfix/` 브랜치는 결정 로그에 **`유출 경로:`** 1줄을 필수 기록한다. 형식:

```
유출 경로: <stage-7의 놓친 렌즈, 또는 "파이프라인 외 기원"(레거시/외부 의존성)>
          / 발생: <이 결함을 만들었거나 가장 먼저 잡았어야 할 단계 —
                   0 탐색 · 1 명세 · 2 영향맵 · 3 설계 · 4 테스트 · 5 구현 ·
                   6 검증 · 외부>
```

CI process-audit은 `유출 경로:` 존재를 강제한다 (`발생:`은 프로즈 규칙 — 강제
승격은 누락이 관측되면). 분기마다 이 라인들을 모아 **발생 단계별로 먼저**
되먹인다: 같은 발생 단계에서 2+건이면 **그 단계의 비평가/체크리스트**가 갱신
대상이다 — 오류는 발생 단계에서 잡는다. 07 렌즈 갱신은
발생 단계를 특정하지 못한 경우의 차선이다. 이것이 파이프라인이 자기 실패에서
배우는 유일한 경로다.

## 컨벤션 갱신 정책

`.agents/context/codebase-conventions.md`는 레포의 실제 코드 패턴을 반영한다.

- **갱신 시점**: 아키텍처 패턴이 변경되는 PR에서 같이 업데이트.
- **갱신 방법**: 0단계(코드베이스 탐색)를 다시 실행하여 재생성. **내용은 갈아엎어도
  `##` 섹션 이름은 남긴다** — 이유와 목록은 그 파일 머리말이 소유한다.
- **갱신 주체**: 패턴을 변경한 PR의 작성자.

## 파이프라인 버전

**버전 번호와 변경 이력은 이 파일이 소유하지 않는다.** 이 `.agents/` 가 어느
커널에서 왔는지는 `.agents/context/.moru-kernel-version` (moru-init 이 기록)이
말하고, 무엇이 왜 바뀌었는지는 git 히스토리와 `docs/adr/` 가 소유한다.

- 이 파일에 버전 문자열을 적지 않는다 — 손으로 적은 문자열은 기계가 쓴 표식과
  갈라지고, 원천 레포의 커널 번호를 대상 레포에서 올리면 아무 업데이트도 합칠 수
  없는 두 번째 버전 계보가 생긴다.
- `.agents/` 를 바꾸는 PR은 변경 이유를 **커밋 메시지**에 남긴다. 전역 영향
  결정이면 § 전역 결정 기록대로 `docs/adr/` 로 승격한다.
- 팀원은 `.agents/` 변경 PR에 대해 반드시 리뷰한다.
