# Feature Development Pipeline

AI 에이전트가 기능 개발 시 따라야 하는 워크플로우 정의.
이 파일은 레포에 독립적이며, 어떤 프로젝트에든 그대로 적용할 수 있다.

- 레포별 코드 패턴 → `.agents/context/codebase-conventions.md`
- 팀 운영 규칙 → `.agents/team-policy.md`

## 핵심 정책

| 정책 | 규칙 |
|------|------|
| **Test-First** | 테스트를 먼저 작성. 레이어는 **축 4개**(격리·결합·계약·전체 경로)로 배정하고 이름·도구는 레포가 번역한다 — 축 정의·예시·배정 표는 `04-test-generation.md` §1이 소유한다. 기본 순서는 격리 → 결합이나 기능 특성에 따라 조정 (예: 마이그레이션은 결합 우선). 구현은 red-green-**refactor** — green 후 작성자가 리팩터 1패스(설계 없는 유연성 금지) 후 리뷰로 넘긴다 |
| **관측 가능성** | 런타임 표면이 있는 기능은 실패가 프로덕션에서 보이도록 설계·구현·검증한다: 3단계 관측 설계(로그/지표/외부호출 타임아웃) → 5단계 계측 → 6단계 에러 경로 방출 확인 → 7단계 #8 렌즈. 순수 데이터/문서/설정 변경은 N/A |
| **테스트 보호** | 4단계 완료 ~ 7단계 완료 동안 테스트 수정 금지. 에러 통과를 위해 테스트를 임의로 수정하지 않음. 리뷰 통과 후 LOCK 해제. 규범 + 기계 강제: 4단계가 `.agents/context/locks/<feature>.lock` 생성 → Claude Code PreToolUse 훅(`scripts/test_lock_guard.sh`)이 `tests/` **편집 시점** 차단 + pre-commit `test-lock` 훅이 커밋 차단 → 7단계 통과 시 삭제. 테스트가 객관적으로 잘못된 경우 사람에게 보고 후 승인받아 수정 (사람이 `sh scripts/unlock_tests.sh <feature>` 실행 — /dev/tty 확인이라 에이전트 단독 불가 — 후 `TEST_LOCK_OVERRIDE=1` 커밋) |
| **테스트 LOCK 전 검수** | 4단계 테스트는 LOCK 전에 작성에 관여하지 않은 상위 모델 에이전트가 설계 대비 검수 (커버리지 누락, 약한 assertion, 설계 불일치 — taxonomy 루브릭 `.agents/context/test-taxonomy.md`로 채점, 적용성은 설계 함의로) + **뮤테이션 검증** (독립 에이전트가 "모든 테스트를 통과하는 스펙 위반 구현"을 연산자 5종으로 시도 — 뚫리면 테스트 보강 후 재시도) + **결정성 게이트** (새 테스트 2회 그린 — flaky는 곧 잘못 잠긴 테스트). 잘못 잠긴 테스트가 가장 비싸다 |
| **독립 리뷰** | 구현에 관여하지 않은 별도 에이전트들이 7단계 리뷰 수행. 렌즈별 finder 3명(coverage-first) → verifier가 blocker/major를 반박 검증 (**프로브 우선**: 실행 가능한 후보는 재현 스크립트를 돌려 런타임 관찰로 판정) → 게이트 대상 기능의 PASS면 2차 verifier가 "검증하지 못한 것"+기각된 blocker/major 전부 재검토, 이견 시 사람 에스컬레이션 (비게이트는 1차 PASS 확정). 리뷰어는 코드를 직접 수정하지 않음 (리뷰/수정 주체 분리) |
| **판단의 실행 환원** | 같은 모델 계열을 겹쳐도 공통 맹점은 안 사라진다 — 판정이 실행으로 가능한 곳(테스트·프로브·e2e·마이그레이션 실행)에서는 추론 대신 실행 결과로 판정한다. 설계·분석이 기존 코드를 참조할 때는 기억이 아니라 파일을 열어 확인한다 |
| **하네스 우선 (skill-first)** | 실질 작업(다중 소스 조사·코드 리뷰·PR 생성·무거운 생성)을 **직접 실행하기 전에** 그 작업을 커버하는 하네스 스킬/커맨드가 있는지 먼저 확인한다 — 있으면 그걸 통해 실행한다. 스킬에 비용 티어링(예: 조사는 haiku 팬아웃)·엄밀성이 이미 설계돼 있어, 메인 세션에서 직접 하면 그 이득을 버린다 (메인 루프 툴 호출은 세션 모델로 돎 — 자동 대체 없음). 예: 다중 소스 조사→`/research`, 리뷰→`/agent-review`, PR→`ship-pr`. 사소·일회성만 직접 하되, 스킬을 건너뛰면 그 사유를 밝힌다 |
| **가정 대장** | 요구사항에 없는 걸 에이전트가 스스로 정한 순간마다 기록 (다른 해석 + 선택 이유 포함). 설계 게이트 승인은 가정 대장 포함 상태에서만 요청 |
| **게이트 브리핑** | 게이트 승인 요청은 비개발자용 브리핑 형식: 잘못되면 생기는 일, 되돌리기 난이도, 사람이 물어봐야 할 질문 3개, Devil's Advocate 위험 3개 (원문) |
| **검증 불가 명시** | 7단계 verdict에 "검증하지 못한 것" 섹션 필수. PASS여도 리뷰가 확인 못 한 범위를 사람에게 노출 |
| **준수 감사 (CI)** | PR마다 `process-audit`이 산출물 체인 존재, stage 7 verdict 실재, 게이트 조건의 diff 기반 독립 재도출을 검사. 파이프라인이 돌았다는 증거 없는 PR은 레드. 우회는 `audit-exempt` 라벨 + PR 본문 사유 (조용한 우회 없음) |
| **코드 재활용** | 기존 코드를 반드시 먼저 탐색. 탐색 결과를 산출물에 명시. 중복 코드 생성 금지 |
| **설계 게이트** | 조건부: API/DB 변경, 의존성 추가, 공개 인터페이스 변경, 기존 동작 변경이 포함된 경우 사람 승인 필수. 단순 추가(내부 유틸, 리팩터링 등)는 설계 산출물 작성 후 바로 진행 |
| **범위 준수** | 요구사항에 없는 것을 확대 해석하거나 임의로 추가하지 않음 |
| **모호함 → 질문** | 여러 방안, 누락, 불확실한 점 → 반드시 사람에게 물어봄 |
| **비판적 검토** | 설계 게이트 대상(되돌리기 어려운 결정)에 대해서는 사람의 지시라도 추가 고려사항과 대안을 검토한다. 더 나은 방안이 있으면 트레이드오프와 함께 사람에게 논의를 제안한다. 단, 비즈니스 흐름과 일정을 우선할 수 있으므로 강제하지 않는다. 선택하지 않은 대안은 결정 로그에 기록한다 |
| **결정 로그** | 각 단계 완료 시 핵심 결정사항을 `.agents/context/decisions/{feature-name}.md`에 append한다. Compaction이 일어나도 이 파일로 진행 상태와 의사결정을 복원한다 |
| **사람을 위한 설명** | AI가 작성한 모든 산출물과 코드는 사람이 이해할 수 있어야 한다. 설계에는 "왜 이 방안인지" 근거를, 코드에는 비자명한 로직에 주석을, 완료 시에는 구현 요약을 포함한다 |

## 파이프라인 흐름

```
유저 요구사항 입력
      │
      ▼
브랜치 생성 (feat/<이름>) = feature-name 확정
      │  결정 로그·artifacts·LOCK 마커가 전부 이 이름으로 묶인다
      ▼
0. 코드베이스 탐색 & 영향 분석   → .agents/00-codebase-discovery.md
      │
      ▼
1. 기획 분석                    → .agents/01-planning.md
      │  완결성 비평가: "명세가 안 정한 것" 목록 → 질문/가정으로 처리
      │  요구사항별 수용 기준(검증 가능) + 범위 밖(non-goals) 명시
      │  (모호한 점 → 사람에게 질문)
      ▼
2. 기능 추출 & 영향 맵           → .agents/02-feature-analysis.md
      │  영향 맵 독립 검증: 비평가가 코드베이스를 열어 누락 파일·숨은 커플링 확인
      │  (불확실 → 사람에게 질문)
      ▼
3. API/DB 설계 + 통합 계획       → .agents/03-design.md
      │  도메인 스킬 로딩 → 솔루션 접근 결정(§0-2: 후보 비교 + 파생 요구사항 R-D*)
      │  → 게이트 대상: 4안 병렬(렌즈 3 + deep 1) → judge rubric 채점·합성
      │  가정 대장 + Devil's Advocate + 정합 셀프체크
      │  관측 설계 + 호환성·폐기 + 롤아웃 (조건부)
      │  (여러 방안 → 사람에게 선택 요청)
      │  (누락 발견 → 사람에게 확인)
      ▼
 ┌──────────────────────────────────┐
 │  설계 게이트 (조건부)               │
 │  API/DB 변경, 의존성 추가,          │
 │  공개 인터페이스 변경, 기존 동작 변경  │
 │  → 🧑 사람 승인 필수               │
 │  그 외 → 설계 산출물 작성 후 바로 진행 │
 │  거부 → 해당 단계 재실행             │
 └──────────┬───────────────────────┘
            ▼
4. 테스트 코드 생성 (Test-First)  → .agents/04-test-generation.md
      │  독립 검수(taxonomy) + 뮤테이션(연산자 5종) + 결정성(2회 그린) 통과 후 테스트 보호 🔒
      ▼
5. 기능 구현                    → .agents/05-implementation.md
      │  테스트를 통과시키는 코드 작성 → green 후 셀프 리팩터 + 관측 계측
      │  테스트 수정 금지 🔒
      ▼
6. 검증 + 실패 분류              → .agents/06-verification.md
      │  린트 → 타입 체크 → 테스트 → e2e 실기동 (+ 롤백 왕복 + 신규코드 커버리지 + 관측 방출)
      │  실패 시 원인 분류 → 해당 단계로 라우팅
      ▼
7. 독립 리뷰 + 리팩토링           → .agents/07-review.md
      │  렌즈 finder 3명 병렬 → verifier 반박 검증 (프로브 우선) → 단독 판정
      │  게이트 대상 + PASS면 2차 verifier 재검토 (이견 → 사람)
      │  "검증하지 못한 것" 섹션 필수
      │  blocker/major → 5단계 리팩토링 → 6 → 7 재리뷰 (최대 2회)
      ▼
   완료 (테스트 LOCK 해제 = 마커 삭제. 잊으면 다음 tests/ 커밋이 훅에 막힌다)
      │
      ▼
   ship-pr 스킬로 PR 생성 (브랜치 + PR, 규칙은 team-policy.md)
```

## 실행 방법

### 자동 라우팅 (경로를 모를 때의 기본 진입점)

```
/dev "요구사항"
```

요구를 해석해 변경 유형(feat/fix/hotfix/refactor/chore/docs)과 게이트 조건을
분류하고, 해당 경로를 조립해 실행한다. 생략은 **정책 어휘**(경로 프리셋 ·
비게이트 · 사전 승인 패턴 · e2e 생략+사유) 안에서만 허용되며, 라우팅과 생략
근거를 결정 로그 첫 블록에 기록한다 — 어휘 밖 생략이 필요하면 사람에게 질문.
오분류는 CI process-audit이 diff에서 게이트를 재도출해 잡는다 (라우터는 제안,
감사가 판정). 상세는 플러그인의 `${CLAUDE_PLUGIN_ROOT}/commands/dev.md` — 단계 내용 자체는 아래 `.agents/` 파일들이 소유한다.

### 전체 파이프라인 실행

모든 단계를 순서대로 실행한다.

```
/feature-dev "기능 설명"
```

### 개별 단계 실행

특정 단계만 실행한다. 이전 단계 산출물이 없으면 코드베이스에서 최소 컨텍스트를 복원하되, 산출물의 "누락 입력" 섹션에 무엇이 빠졌는지 명시한다.

```
/discover     → 0단계: 코드베이스 탐색
/plan         → 1단계: 기획 분석
/analyze      → 2단계: 기능 추출
/design       → 3단계: API/DB 설계
/gen-tests    → 4단계: 테스트 생성
/implement    → 5단계: 구현
/validate     → 6단계: 검증
/agent-review → 7단계: 독립 리뷰
```

**커맨드는 이 레포에 복사되지 않는다 — moru 플러그인이 제공한다**
(`${CLAUDE_PLUGIN_ROOT}/commands/`). 각 커맨드는 이 레포의 `.agents/` 해당 단계
파일(`00-*.md`~`07-*.md`)로 위임하므로, 커맨드 본문은 얇고 **실제 내용은 여기
있다.** 플러그인이 설치돼 있으면 `/dev` 같은 슬래시 커맨드가 그대로 뜨고, 없으면
해당 단계 파일을 직접 읽고 수행하면 된다 — 다른 AI 도구도 마찬가지다.

## 단계별 산출물 체인

**저장 규약**: 각 단계 산출물은 대화에만 남기지 않고 파일로 저장한다 —
`.agents/context/artifacts/{feature-name}/NN-<stage>.md` (예: `03-design.md`).
다음 단계·서브에이전트·개별 커맨드 실행은 이 파일 경로를 입력으로 받는다.
결정 로그는 "핵심 결정" 요약, artifacts는 산출물 전문 — 역할이 다르다.
7단계 통과 후 머지되면 artifacts는 PR에 포함되어 이력이 된다.
(CI process-audit이 실재를 강제하는 것은 01/02/03/04/06/07 — 00/05는 규약상
저장하되 감사 비대상: 00은 코드베이스에서 재도출 가능하고 05의 실체는 diff 자체다.)

각 단계는 반드시 다음 구조의 산출물을 포함해야 한다:

```markdown
## [N단계] 산출물

### 입력
- 이전 단계에서 받은 것: [목록]
- 누락 입력: [없으면 "없음". 개별 실행 시 무엇이 빠졌는지]

### 결과
[단계별 고유 내용]

### 종료 조건
- [ ] [이 단계가 완료되었다고 판단하는 조건]

### 실패 시
- [실패 유형] → [라우팅 대상]
```

산출물 체인 (각 단계 완료 시 결정 로그에도 append):

```
0단계 → 코드베이스 컨텍스트 + 재활용 가능 자산 목록          📝 결정 로그 생성
  ↓
1단계 → 요구사항 명세 (수용 기준 + non-goals 포함)          📝 결정 로그 append
  ↓
2단계 → 기능 목록 + 영향 맵 + 재활용 매핑                  📝 결정 로그 append
  ↓
3단계 → 설계 문서 (솔루션 접근 + 파생 요구사항 + API + DB + 통합계획 + 비즈니스 규칙 + 에러 정책 + 관측 설계 + 호환·롤아웃 + 가정 대장 [+ 4안 비교 + 게이트 브리핑])  📝 결정 로그 append
  ↓ (조건부 🧑 승인)
4단계 → 테스트 코드 🔒                                    📝 결정 로그 append
  ↓
5단계 → 구현 코드 (테스트 통과 + 셀프 리팩터 + 관측 계측)      📝 결정 로그 append
  ↓
6단계 → 검증 결과 (e2e + 커버리지 + 관측 방출) + 구현 요약 + 실패 시 원인 분류   📝 결정 로그 append
  ↓
7단계 → 검증 생존 findings + "검증하지 못한 것" + 판정 (PASS/REFACTOR/ESCALATE)  📝 결정 로그 최종화
```

## 실패 시 라우팅

| 실패 유형 | 원인 분류 | 라우팅 |
|-----------|----------|--------|
| 린트/타입 에러 | 구현 코드 문제 | → 5단계 재실행 |
| 테스트 실패 | 구현이 스펙을 충족 못 함 | → 5단계 재실행 (테스트 수정 X) |
| e2e 실기동 실패 | 배선(라우터/DI/설정) 또는 마이그레이션 문제 | → 5단계 수정 (분류 기준은 06 원인 분류표). 스키마 설계 결함이면 사람 확인 후 3단계 |
| 테스트 자체 오류 의심 | 테스트가 설계를 잘못 반영 | → 사람에게 보고, 승인 후 4단계 수정 |
| **의도된 기존 동작 변경으로 기존 테스트 깨짐** | 설계가 그 동작을 바꿈 (회귀 아님) | → 사람 승인 후 4단계에서 기존 테스트 갱신 (`TEST_LOCK_OVERRIDE=1`, 결정 로그). 설계 대조로 회귀와 구분 |
| 같은 원인으로 2회 연속 실패 | 저비용 모델의 판단 한계 가능성 | → 3회째 5단계 재실행은 **최상위 모델(fable) fresh-context 서브에이전트로 승급** — 실행 주체·입력·기록 규칙은 `06-verification.md` §4 |
| 3회 연속 실패 | 구현으로 해결 불가 | → 사람에게 보고 |
| 설계 결함 의심 | 테스트/구현 모두로 해결 불가 | → 사람 확인 후 3단계부터 재실행 |
| **개발 중 요구사항 추가/변경** | 기획 변경 (에자일 반복) | → 3단계 통째 재실행 금지. **독립 파급 판정 → 델타 재설계** (`03-design.md` §9): 교차 없음=amendment만, 기존 항목 영향=부분 재설계, 설계 근간 변경=풀 재실행 승격 |
| 리뷰 blocker/major | 품질/규칙 위반 | → 5단계 리팩토링 (테스트 LOCK 유지) 후 6→7 재실행 |
| 리뷰 finding — 테스트 품질 | 약화된 assertion, 커버리지 누락 등 테스트 자체 결함 | → 사람에게 보고, 승인 후 4단계 수정 (`TEST_LOCK_OVERRIDE=1` 커밋, 결정 로그 기록) → 6→7 재실행 |
| 재리뷰 2회 후에도 blocker | 리팩토링으로 해결 불가 | → 사람에게 보고 |

## 설계 게이트 조건

다음 중 하나라도 해당하면 사람 승인 필수:

- [ ] API 엔드포인트 추가/변경
- [ ] DB 스키마 변경 (테이블, 컬럼, 인덱스)
- [ ] 새 패키지 의존성 추가 (의존성 매니페스트 — repo-profile `DEPS_MANIFEST`, 예: `pyproject.toml`)
- [ ] 기존 공개 인터페이스 변경 (기존 코드의 동작이 바뀜)
- [ ] 환경변수/설정 추가
- [ ] **고위험 경로** (team-policy "위험 차등 게이트"): 인증/인가, 프로덕션 설정·
  시크릿, PII·결제 로직 — 경로 목록은 repo-profile `HIGH_RISK_PATH_RE`가 소유
  (레포별 재생성, 예: FastAPI라면 `app/core/security.py`). 이 항목은 사전 승인
  패턴으로도 우회 불가

해당 없으면 설계 산출물 작성 후 바로 4단계로 진행.

**사전 승인 패턴 (승인 피로 완화, 선택)**: 사람이 `.agents/context/pre-approved-patterns.md`에
패턴을 등록하면 (예: "표준 CRUD 리소스 추가 — BaseRepository/BaseService 확장, 신규 테이블 1개,
기존 테이블 무변경"), 그 패턴에 **완전히** 부합하는 변경은 게이트 브리핑 승인과 **best-of-4·Devil's
Advocate를 생략**하고 단일 설계로 진행하며 (03-design.md §6-1 — 내력벽인
LOCK·뮤테이션·독립 리뷰는 그대로), 결정 로그에 "사전 승인 패턴 적용: <패턴명>"만
기록한다. 패턴 경계를 조금이라도 벗어나면 (기존 테이블 변경, 의존성 추가 등)
일반 게이트로 승격. 가정 대장은 생략하지 않는다.

## 결정 로그 (Decision Log)

### 목적

피처 개발 중 핵심 의사결정을 파일로 기록하여:
1. **Compaction 내성**: 대화 컨텍스트가 유실되어도 진행 상태와 결정 이력을 복원
2. **인수인계**: 사람이 바뀌어도 왜 이렇게 만들었는지 추적 가능
3. **대안 기록**: 선택하지 않은 방안도 남겨서 나중에 재검토 가능

### 파일 위치

```
.agents/context/decisions/{feature-name}.md
```

피처 이름은 브랜치 이름과 동일하게 (`user-auth`, `product-catalog` 등).

### 기록 규칙

각 단계 **진입 시** `## N단계 진행중 (YYYY-MM-DD)` 1줄을 먼저 append한다 —
스테이지 도중 세션이 끊겨도(compaction) 재개 에이전트가 "N단계 도중"임을 알 수 있고,
lock 마커 존재 vs 로그 상태의 불일치를 조정할 수 있다 (진행중 4단계 + lock 존재 =
정상 진행 중, 완료 로그 없이 lock만 존재 = 4단계 도중 단절 → 4단계 재개).

각 단계 완료 시 결정 로그에 다음을 **append**한다:

```markdown
## N단계 완료 (YYYY-MM-DD)
- **핵심 결정**: [무엇을 어떻게 하기로 했는지]
- **근거**: [왜 이 방안인지]
- **검토한 대안**: [대안과 선택하지 않은 이유. 없으면 "없음"]
- **🧑 사람 결정**: [사람이 내린 결정이 있으면 기록. 없으면 생략]
- **기준 커밋**: [실행 결과 해시 값 (예: `abc1234`) + 작업 트리 dirty면 "+미커밋 변경"
  표기 — 이 단계 판단이 어느 코드 상태 기준이었는지. 사후 감사·재개 시 정합 확인용]
- **소요**: [에이전트 호출 수, 재시도 횟수. 대략치면 충분 — 비용 가시성용]
- **장치 적중**: [해당 단계의 검증 장치가 실제로 뭔가 잡았는지 — 예: "영향맵 비평가 지적 2건",
  "뮤테이션 1라운드 뚫림→테스트 1개 보강", "2차 verifier 동의", "DA 위험 1건 채택".
  잡은 게 없으면 "적중 없음". 기능 5~10개 누적 후 적중 0인 장치를 조건부로 강등하는 근거]
- **현재 상태**: [다음에 할 것]
```

### Compaction 복원 절차

대화 컨텍스트가 유실(compaction)된 경우 — 사람 입장에서는 "에이전트 세션이 끊겼거나
에이전트가 갑자기 맥락을 잊은 것처럼 보일 때":

1. `.agents/context/decisions/` 디렉토리에서 진행 중인 피처 로그를 읽는다
2. 로그의 "현재 상태"를 확인하여 어디서부터 재개할지 판단한다
3. 해당 단계의 이전 산출물이 필요하면 로그에서 복원하거나, 코드베이스에서 최소 컨텍스트를 수집한다
4. 유실된 맥락이 있으면 사람에게 확인한다
