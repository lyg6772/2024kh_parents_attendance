# 7단계: 독립 리뷰 + 리팩토링

## Role

구현에 관여하지 않은 **독립 에이전트**가 코드를 리뷰하고, 리팩토링이 필요하면
5단계로 라우팅한다. 이 단계를 통과해야 기능 개발이 완료되고 테스트 LOCK이 해제된다.

## Input

- 3단계 산출물: 설계 문서
- 5단계 산출물: 구현 코드 (브랜치 diff)
- 6단계 산출물: 검증 결과 (전부 그린이어야 함)
- 결정 로그: `.agents/context/decisions/{feature-name}.md`
- `.agents/context/codebase-conventions.md`의 "숨은 결합" 레지스트리 (리뷰어 컨텍스트에 포함)

## Process

### 1. 독립 컨텍스트 (필수)

구현 대화를 본 에이전트가 리뷰하면 자기 코드에 관대해진다.
**반드시 구현 컨텍스트가 없는 새 에이전트(서브에이전트/새 세션)로 실행한다.**
리뷰어에게 제공하는 것: 설계 문서 + 브랜치 diff + 이 파일 + `AGENTS.md` +
conventions "숨은 결합" 레지스트리. 그 외 대화 이력 제공 금지.

### 1-1. 다중 렌즈 리뷰 (finder → verifier 2단 구조)

리뷰어 1명의 판단에 의존하지 않는다. 구조:

1. **렌즈 finder 3명 병렬** (fresh-context 서브에이전트, 저비용 모델, 각자 렌즈 1개):
   - **spec-일치**: 설계 문서 대비 누락·다르게 구현된 것, 그리고 **설계에 없이
     추가된 것**(요구에 없는 추상화·설정·유연성 = 과잉 설계 — 같은 렌즈의
     반대 방향) (체크리스트 #1, #5)
   - **correctness**: edge case, 동시성, 트랜잭션 경계, 에러 경로, 명백한 자원
     낭비 — 루프 내 쿼리(N+1)·페이지네이션 없는 전량 조회·async 경로의 동기 I/O (#2).
     **에러 경로 관측**(#8): 설계 §3-2가 로그/지표를 정의했는데 에러 경로가 진단
     신호 없이 조용히 실패하면 프로덕션에서 안 보인다 — 설계에 관측이 있을 때만 본다
   - **security + 규칙**: 신뢰 경계 검증, 시크릿, authz, 계층/재사용 규칙 위반 (#3, #4, #7).
     **vibe-coding 상습 결함 체크리스트** (AI 생성 코드 사고의 최빈 유형 — 엔드포인트마다 순회):
     ① 엔드포인트별 인가 — 인증만 있고 인가가 없는 경우 (타인 리소스 ID로 접근하면? IDOR)
     ② mass assignment — 요청 스키마가 권한/역할/소유자 필드를 받는 경우
     ③ 디버그·관리용 엔드포인트가 프로덕션 라우터에 노출
     ④ CORS 와일드카드, rate-limit 부재 (인증 엔드포인트), 에러 응답의 내부 정보 누출
   - finder 지침: **coverage-first** — 확신 없는 것, 사소해 보이는 것도 전부 보고한다.
     중요도 필터링은 finder의 일이 아니다 (검증 단계가 거른다). 각 finding에
     확신도(높음/중간/낮음)를 붙인다.
   - **심층 적대 렌즈 (게이트 대상·고위험 변경에만)**: 위 3개 저비용 finder에 더해
     `adversarial-reviewer`(상위 모델)를 **4번째 finder로 병렬** 실행한다 — sonnet
     finder가 놓치는 미묘한 정확성/로직/동시성/트랜잭션·설계 결함, 그리고 **변경의
     파급(blast-radius)·숨은 결합을 diff 밖으로 넓혀 발굴**한다 (실측상 상위 모델의
     이득은 "어디를 더 파볼지" 넓히는 발굴형 작업에 몰려 있어 — diff만 보게 두면
     낭비다). 발굴한 숨은 결합은 "숨은 결합 발견" 섹션에도 올린다. 단 finding은 이
     변경의 파급으로 추적돼야 하고, 무관한 기존 결함은 이 게이트 범위가 아니다.
     **보안은
     다루지 않는다** — security+규칙 finder와 verifier의 필수 authz 프로브가 담당한다
     (중복 방지 + 상위 모델의 보안분석 거부·약화 회피). 출력은 다른 finder와 동일
     형식이고, verifier가 동일하게 반박 검증한다. **비게이트·사소 변경엔 생략**한다
     (상위 모델 비용 — 게이트 조건은 `workflow.md` § 설계 게이트 조건 어휘를 따른다).
2. **verifier 겸 judge 1명** (`cto-reviewer`, 상위 모델): finder들의 finding을
   (게이트 대상이면 심층 적대 렌즈 포함) 중복 제거 후,
   blocker/major 후보마다 **반박을 시도**한다 ("이게 진짜 버그인가? 재현 경로는?").
   반박에 살아남은 finding만 채택하고, 기각된 finding은 기각 근거와 함께 기록한다.
   체크리스트 **#6(테스트 품질)·#9(유지보수)는 렌즈 배정이 없으므로 verifier가 직접
   커버**한다 (4단계 검수·뮤테이션이 상류를 지키지만, 구현 중 추가된 테스트는 여기서만
   보인다. #9는 취향이 아니라 다음 사람의 이해가능성만 — 네이밍·함수 크기·읽기 난이도).

   **프로브 우선 (판정을 실행으로 환원)**: 후보가 실행으로 재현/반증 가능하면
   (동시성 경합, 트랜잭션 경계, 에러 경로, 마이그레이션 정합) 순수 추론으로
   판정하지 않는다 — 최소 재현 프로브(스크립트/pytest 1개, **레포 밖** 임시
   디렉토리에 생성 — 레포 안에 두면 커밋 오염 위험)를
   **작성·실행**하고 런타임 관찰로 채택/기각한다. 모델이 못 보는 결함도 실행은
   드러낸다. **양성 대조 필수**: 기각(버그 없음) 방향 프로브는 일부러 결함을 주입한
   변형에서 먼저 실패하는지 확인한 뒤 원본에 돌린다 — 안 깨지는 프로브는 결함을
   자극 못 하는 무효 프로브다. 실행 불가능한 후보(설계 판단, 컨벤션)만 추론으로
   판정하되 산출물에 `추론 판정`으로 표시한다. 프로브 파일은 판정 후 삭제 (커밋 금지).
   **authz 프로브 의무**: diff에 신규/변경 엔드포인트가 있으면, finding 유무와
   무관하게 **권한 없는 사용자(무토큰 + 타인 계정 토큰)로 실제 요청하는 프로브**를
   최소 1개 실행한다 — 401/403/404가 아니면 blocker. AI 생성 코드의 최빈 실사고가
   인가 누락(IDOR)이라 이것만은 상시 실행이다.
   1차 verdict는 verifier가 단독으로 낸다.

3. **2차 verifier (게이트 대상 기능의 PASS 확정 전)**: 1차 verdict가 PASS이고
   기능이 **설계 게이트 대상**(또는 고위험 경로)이면, 별도 fresh-context
   에이전트(**저비용 모델** — 가치는 능력 우위가 아니라 앵커링 없는 독립 재프로브고,
   판정은 pytest/프로브가 낸다)가 **"검증하지 못한 것" 목록 + 기각된 blocker/major 전부**만
   재검토한다 (표본 선별 금지 — 선별 주체가 약한 기각만 고를 수 있다).
   fail-safe: 잘못 동의해도 바닥은 1차(상위 모델)의 PASS, 잘못 이견이면 사람 에스컬레이션.
   비게이트 기능·사전 승인 패턴은 1차 PASS로 확정한다 (토큰 티어링 — 이중 검증은
   되돌리기 비싼 곳에만) — 실행 가능한 항목은 프로브로 직접 확인한다. 입력: 설계 문서 + diff +
   1차 verifier의 해당 두 섹션. 1차의 살아남은 finding 목록은 주지 않는다 (앵커링 방지).
   - 2차가 동의 → PASS 확정.
   - 2차가 신규 blocker/major를 내거나 기각에 반대 → **사람에게 에스컬레이션**
     (두 판정을 나란히 첨부). 에이전트끼리 재판정 루프 금지.
   REFACTOR/ESCALATE verdict는 2차 없이 그대로 라우팅한다 (이중 검증은 통과 방향에만).
   fix/hotfix의 7-축소 리뷰(team-policy — verifier 1명)에서는 2차 verifier도 생략한다.

**컨텍스트 규약**: finder 입력 = 설계 문서 + diff + 자기 렌즈 정의 + 숨은 결합
레지스트리뿐. finder 출력 = finding 형식 행당 1줄 (해설 금지). verifier 입력 =
finder 출력 + 설계 문서 + diff + 숨은 결합 레지스트리
(spec-일치 finding을 반박 검증하려면 설계 문서가 필요하다).

### 2. 리뷰 체크리스트 (우선순위순)

| # | 항목 | 기준 |
|---|------|------|
| 1 | 요구사항/설계 충족 | 설계 문서 대비 빠지거나 다르게 구현된 것 |
| 2 | 정확성·자원 | edge case, 동시성, 트랜잭션 경계, 에러 경로, 명백한 자원 낭비 (N+1, 페이지네이션 없는 전량 조회, async 경로 동기 I/O) |
| 3 | 계층 규칙 | `AGENTS.md` Critical Rules 위반 (컨트롤러 비즈니스 로직, `HTTPException` 등) |
| 4 | 재사용 | 기존 base/헬퍼가 있는데 중복 구현한 것 |
| 5 | 과잉 설계 | 요구에 없는 추상화·설정·유연성 → 삭제 제안 |
| 6 | 테스트 품질 | 테스트가 실질을 검증하는지, 약화된 assertion은 없는지 |
| 7 | 보안 | 신뢰 경계 입력 검증, 시크릿, 로그 내 민감정보, 엔드포인트별 인가(IDOR), mass assignment, 디버그 엔드포인트 노출, CORS/rate-limit |
| 8 | 운영 가시성 | 에러 경로에 진단 가능한 로그/지표가 있나 (설계 §3-2 대비). 조용한 실패 = 프로덕션 미가시 (설계에 관측 없으면 N/A) |
| 9 | 유지보수 | 가독성·네이밍·함수 크기 — 다음 사람이 읽고 고칠 수 있나. 취향 아닌 이해가능성만 |

### 3. Finding 형식

```
[blocker|major|minor] file:line — 문제 한 줄 — 제안 한 줄
```

- **blocker**: 요구사항 미충족, 정확성 버그, 보안 결함
- **major**: 계층/재사용 규칙 위반, 과잉 설계
- **minor**: 기록만 하고 통과 가능

### 4. 라우팅

| 판정 | 라우팅 |
|------|--------|
| blocker/major 있음 | → 5단계 리팩토링 (테스트 LOCK 유지) → 6단계 재검증 → 7단계 재리뷰 (델타 — 아래) |
| **테스트 품질 finding** (약화된 assertion, 커버리지 누락 — 체크리스트 #6) | → 사람에게 보고, 승인 후 4단계에서 테스트 수정 (`TEST_LOCK_OVERRIDE=1`, 결정 로그 기록) → 6 → 7 재실행. 5단계로 보내지 않는다 — 구현은 문제가 아님 |
| minor만 있음 | → 결정 로그에 기록 후 통과 |
| 설계 자체 결함 | → 사람에게 보고 (필요 시 3단계 재실행) |
| **재리뷰 2회 후에도 blocker** | → 사람에게 보고. 무한 루프 금지 |

### 4-1. 재리뷰 (델타 리뷰)

REFACTOR 후 재리뷰는 finder 3명을 풀 재실행하지 않는다:

- **verifier(cto-reviewer)만** 재실행: 입력 = 리팩토링 diff(이전 리뷰 이후 변경분) +
  이전 리뷰의 blocker/major 목록. 확인 범위 = ① 각 blocker/major가 실제 해소됐는가
  (실행 가능하면 프로브 재실행) ② 리팩토링이 새로 만든 문제.
- **풀 재리뷰로 승격하는 조건**: 리팩토링이 이전 리뷰 diff에 없던 파일을 건드렸거나,
  공유 코드(base 클래스, deps, core)를 수정했으면 finder 3명부터 다시 (델타 밖
  파급은 verifier 혼자 못 본다).
- 2차 verifier는 재리뷰 최종 PASS에도 동일 적용 (feat 한정).

안 바뀐 코드는 이미 검증 통과 + LOCK된 테스트가 지키는 상태라 다시 보지 않는다.

### 5. finder 출력 불량 처리

finder가 빈 출력 또는 Finding 형식이 아닌 출력을 반환하면 **해당 finder만 1회 재실행**한다.
재실행도 불량이면 그 렌즈는 "무효"로 기록하고, verifier가 해당 렌즈 관점을 직접 커버한 뒤
산출물에 렌즈 무효 사실을 명시한다 (조용히 2렌즈로 축소 금지).

## Output 템플릿

```markdown
## [7단계] 리뷰 산출물

### 입력
- 설계 문서 / diff 범위: [명시]
- 누락 입력: [없으면 "없음"]

### Finder 원출력 (렌즈별 — 실행 증거)
각 finder의 finding 줄을 **가공 없이 그대로** 붙인다 (빈 렌즈는 "finding 없음" +
재실행 여부). 이 섹션이 없으면 CI process-audit이 레드 — 리뷰가 실제로 돌았다는
최소 증거다. verifier가 요약·선별한 버전으로 대체 금지.

- **spec-일치**: [원출력]
- **correctness**: [원출력]
- **security+규칙**: [원출력]
- **심층 적대** (게이트 대상만): [원출력, 또는 "비게이트 — 미실행"]

### Findings (검증 생존만)
| 심각도 | 렌즈 | 위치 | 문제 | 판정 방식 | 제안 |
|--------|------|------|------|----------|------|
(판정 방식: `프로브 — <무엇을 실행했는지 1줄>` 또는 `추론 판정 — <왜 실행 불가인지>`)

### 기각된 findings
| 렌즈 | 위치 | 주장 | 판정 방식 | 기각 근거 |
|------|------|------|----------|----------|

### 2차 verifier (게이트 대상 + PASS인 경우 필수)
- 재검토 범위: [검증하지 못한 것 N건 + 기각 blocker/major M건 전부]
- 프로브 실행: [실행한 것 / 실행 불가 사유]
- 판정: [동의 — PASS 확정 / 이견 — 사람 에스컬레이션 (양 판정 첨부)]
- (비게이트 기능이면 이 섹션 대신: "비게이트 — 1차 PASS 확정" 1줄)

### 숨은 결합 발견
- [새로 발견한 간접 결합 목록, 또는 "없음". 있으면 단계 완료 시 conventions
  레지스트리에 append하고 여기 "append 완료"를 기록]

### 검증하지 못한 것 (필수 — 사람이 읽는 섹션)
PASS여도 이 리뷰가 확인 **못 한** 범위를 명시한다. 무결점처럼 보이는 PASS가 제일 위험하다.

- (정말 없으면 "없음"이 아니라, 왜 전 범위가 커버됐는지 1줄)

### 판정
```

## Rules

- **리뷰어는 코드를 직접 수정하지 않는다.** 리뷰 주체와 수정 주체를 분리한다. 수정은 5단계 재실행으로.
- **finder는 거르지 않고, verifier는 봐주지 않는다.** finder가 자체 필터링하면 recall이 죽고, verifier가 반박 없이 통과시키면 오탐이 산다. 역할을 섞지 않는다.
- **verdict의 근거는 검증 생존 finding만이다.** 기각된 finding으로 REFACTOR를 걸지 않는다.
- 취향 지적 금지 — `AGENTS.md`/conventions 위반과 실질 결함만 finding으로 올린다.
- **숨은 결합 자산화**: 리뷰 과정에서 발견된 간접 결합(이벤트 발행/구독, 런타임
  디스패치, 픽스처 의존 등 정적 분석이 못 잡는 것)은 finding 여부와 무관하게
  산출물 "숨은 결합 발견" 섹션에 보고하고, 단계 완료 시 메인 에이전트가
  `.agents/context/codebase-conventions.md` 레지스트리에 append한다
  (리뷰어 서브에이전트는 파일을 수정하지 않는다).
- 리팩토링 중에도 테스트 LOCK은 유지된다. 테스트가 깨지면 리팩토링이 틀린 것이다.
- **7단계 통과 시 테스트 LOCK 해제**: `.agents/context/locks/<feature-name>.lock` 마커를 **반드시 삭제**하고 (잊으면 이 브랜치의 다음 `tests/` 커밋이 훅에 막힌다), 결정 로그에 리뷰 결과와 "현재 상태: 완료"를 append한다 (결정 로그 최종화).
- **전역 결정 승격 (통과 시)**: 이 기능의 설계에 전역 영향 결정(솔루션 접근 §0-2, 아키텍처 패턴, 정합성 전략 등)이 있으면 `docs/adr/`에 ADR을 추가하고 현황판(`docs/adr/README.md`)을 **같은 커밋**으로 갱신한다 (team-policy §전역 결정 기록). 해당 없으면 생략.
- 통과 후 다음 단계는 `ship-pr` 스킬로 PR 생성 (`team-policy.md` PR 규칙).
