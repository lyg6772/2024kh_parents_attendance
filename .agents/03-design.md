# 3단계: API/DB 설계 + 통합 계획

## Role

기능 목록을 바탕으로 API 인터페이스, DB 스키마, 요청/응답 스키마(스키마 도구는 레포 스택 소유 — 예: Pydantic, zod)를 설계하고 기존 코드와의 통합 계획을 수립한다.

**설계 게이트 조건에 해당하면 이 단계 완료 후 사람의 승인을 받아야 다음 단계로 진행할 수 있다.** (조건은 `.agents/workflow.md`의 "설계 게이트 조건" 참조)

## Input

- 2단계 산출물: 기능 목록 + 영향 맵 + 재활용 매핑
- 0단계 산출물: 코드베이스 컨텍스트

## Process

### 0. 도메인 스킬 로딩 (필수, 설계 시작 전)

2단계 영향 맵을 보고 해당하는 스킬을 **읽고 나서** 설계한다. 스킬 목록·매핑의
소유자는 타깃 레포 AGENTS.md Skill Routing이다 — 아래 표는 예시 매핑:

| 영향 맵에 이것이 있으면 | 읽을 스킬 |
|----------------------|----------|
| 테이블/컬럼/제약조건 | `db-schema` |
| 조회/조인/페이지네이션 | `db-query` |
| 스키마 변경 (기존 테이블) | `db-migration` (expand-contract) |
| 인증/인가/토큰 | `auth` |
| 백그라운드 작업 | `background-jobs` |

설계는 백지 상상이 아니라 스킬의 체크리스트 순회로 한다. Best-of-4 초안
서브에이전트 프롬프트에도 해당 스킬 파일 경로를 포함한다.

### 0-2. 솔루션 접근 결정 (조건부 필수 — 구조 설계 전에)

**트리거 (본질 기준)**: 요구사항은 결과만 말하는데 그 결과에 도달하는 **방법이
2개 이상**이고, 어느 방법을 고르냐가 스키마·에러 정책·테스트를 다르게 만드는
결정이 하나라도 있으면 이 섹션을 먼저 완료한다. 두 계열 모두 해당된다:

- **기술 접근**: 저장소 선택(파일/blob/캐시), 외부 인프라(S3, 큐, CDN 등),
  외부 서비스/API 연동, 전송·처리 방식(presigned URL vs 프록시, 동기 vs 비동기)
- **로직 접근**: 동시성/정합성 전략(낙관적 락 vs 유니크 제약 vs 비관적 락),
  상태 모델(상태 머신 vs 플래그 조합), 계산·집계 방식(실시간 계산 vs 비정규화
  카운터 vs 배치), 권한 모델(역할 vs 소유자 vs ACL), 순서/중복 처리(멱등키,
  position 표현)

해당 없으면(방법이 사실상 하나뿐인 기존 스택 안의 순수 CRUD) "해당 없음 - 이유"
1줄로 건너뛴다.

테이블·엔드포인트는 **이미 정해진 접근의 구조**다. 접근 자체가 미결정인 채
구조 설계로 직행하면 에이전트는 가장 익숙한 접근을 암묵적으로 깔고 그린다 —
접근 선택이야말로 가장 되돌리기 비싼 결정(인프라·외부 계약뿐 아니라 상태
모델·정합성 전략도 스키마와 테스트 전체를 물들인다)인데 탐색 없이 지나간다.

절차:

1. **후보 접근 2~3개**를 표로 비교한다: 접근 / 트레이드오프(정확성·복잡도·
   성능·운영 부담·보안·비용·lock-in 중 해당 축) / 탈락 사유. 후보가 정말
   1개뿐이면 왜 대안이 없는지 1줄. **기술 접근 후보가 있으면**
   `codebase-conventions.md`의 "인프라 컨텍스트" 섹션(사용 가능 인프라, 선호
   벤더, 금지 사항)을 먼저 읽고, 없는 인프라를 전제하지 않는다 — 불명확하면
   사람에게 질문.
2. **선택한 접근의 파생 요구사항**을 도출한다 — 접근이 요구사항을 낳는다.
   기술 예: presigned URL 선택 → 만료 정책, 고아 객체 청소, Content-Type
   화이트리스트, 크기 상한. 로직 예: 낙관적 락 선택 → 충돌 시 409 + 클라이언트
   재시도 정책, 비정규화 카운터 선택 → 정합성 검증/복구 경로. 각 항목에
   **`R-D1, R-D2, …` 번호**를 붙여 산출물에 기록한다. 이 번호는 1단계
   요구사항과 동급으로 취급된다 — 4단계 요구사항 커버리지 표가 함께 순회하고,
   뮤테이션 검증의 판정 기준에 포함된다.
3. 1단계 완결성 비평가가 "필요한 접근 결정"으로 표면화한 항목이 있으면
   전부 여기서 결정하거나 사람 질문으로 승격한다.
4. 게이트 대상이면(인프라·의존성·환경변수는 기존 게이트 조건, 로직 접근도
   기존 동작 변경·API에 걸리는 경우가 대부분) 게이트 브리핑에 이 비교표를
   그대로 첨부해서 **사람이 구조가 아니라 접근을 승인**하게 한다. 접근이
   갈리는 경우는 기존 규칙대로 사람에게 선택 요청.

Best-of-4(§6-1)는 이 접근 결정 **이후** 그 접근 안에서 구조를 변주한다 —
초안 프롬프트에 선택된 접근과 파생 요구사항을 포함한다.

### 1. DB 설계

- 테이블 구조 (컬럼, 타입, 제약조건)
- 기존 테이블과의 관계 (FK 등)
- 인덱스, unique 제약조건

### 2. 스키마 설계

- Create/Update/Response 스키마
- 유효성 검증 규칙

### 3. API 엔드포인트 설계

- HTTP 메서드, 경로, 상태 코드
- 요청/응답 스키마 매핑
- 에러 응답

### 3-1. 비즈니스 규칙 정의 (필수)

구조(테이블·스키마·엔드포인트)가 아니라 **행위**를 정의한다 — 1단계 요구사항에서
도출되는 도메인 규칙을 표로 명세한다 (예: "결제 완료 상태에서만 취소 가능").
이 표가 4단계 테스트·뮤테이션 검증·7단계 spec-일치 finder의 판정 기준이 된다 —
여기 없는 규칙은 어떤 검증 장치도 지키지 못한다.

각 규칙: 규칙 / 입력 조건 / 기대 결과 / 위반 시 (예외 → 에러 정책 표와 정합).
규칙이 정말 없으면 (순수 CRUD) "없음"을 근거와 함께 명시한다.

### 3-2. 관측 설계 (Observability) — 조건부 필수

런타임 표면이 있는 기능이면(순수 데이터/문서/설정 변경은 "N/A - 사유") 실패가
프로덕션에서 **보이도록** 설계한다. 에러 정책 표(§3, 어떤 예외를 반환)와 짝이다 —
정책은 "무엇을 반환하나", 관측은 "무엇이 보이나". 둘 다 없으면 에러 경로가 조용히
500을 내고 운영에서 원인을 못 찾는다.

- **구조적 로그**: 어느 지점에서 어떤 필드로(요청 id·엔티티 id·결과). 특히 에러
  정책 표의 **각 예외 경로** — 그 경로가 로그 없이 실패하면 프로덕션에서 안 보인다.
- **지표/신호**: 성공/실패 카운터, 지연이 요구에 걸리면 지연. 요구가 함의할 때만.
- **알람 가치 조건**: 사람이 개입해야 하는 상태가 있으면 명시 (없으면 생략).
- **외부 호출 있으면**: 타임아웃·재시도·폴백을 여기서 정한다 — 안 정하면 무한
  대기·연쇄 실패가 암묵 기본값이 된다.
- 민감정보(PII·시크릿)는 로그에서 제외 (7단계 보안 렌즈가 재확인).

### 4. Repository 설계

- 기본 CRUD 활용 범위
- 추가 필요한 도메인 특화 메서드

### 5. 통합 계획

- 라우터 등록, 설정 변경, 예외 추가, 패키지 추가

### 5-1. 새 의존성 검증 (새 패키지 추가 시만, 필수)

새 패키지 추가는 이미 게이트 트리거다 — 승인 전에 그 패키지 자체를 확인해
**사람이 근거를 갖고 승인**하게 한다 (공급망 리스크는 되돌리기 비싸다). 추가하는
패키지마다: 알려진 CVE 유무 / 라이선스(프로젝트와 호환되는가) / 유지보수 상태
(최근 릴리스·활동) / **더 가벼운 대안이나 기존 스택으로 대체 가능한가** (YAGNI —
몇 줄로 될 일에 의존성 추가 금지). 결과를 게이트 브리핑에 1줄씩 첨부한다.
기존 의존성만 쓰면 이 절 생략.

### 5-2. 호환성·폐기 전략 (기존 공개 인터페이스 변경 시만)

기존 공개 인터페이스(API 계약, 응답 스키마 필드, 외부가 의존하는 동작)를 바꾸면:
하위호환 유지 여부 / 불가하면 버저닝 / 폐기 창(deprecation window)과 통지 경로.
소비자가 내부뿐이면 "내부 전용 — 즉시 교체" 1줄. 스키마 변경은 db-migration의
expand-contract와 정합시킨다. 순수 추가면 이 절 생략.

### 5-3. 롤아웃 전략 (위험 변경 시만 — 기존 동작 변경·고위험 경로)

바뀐 동작을 **점진 노출·즉시 차단**할 수단을 정한다: 피처 플래그 / kill-switch /
단계 롤아웃. 마이그레이션 안전은 expand-contract가 담당하고, 여기선 코드 동작
쪽이다. 순수 추가(신규 엔드포인트 + 기존 경로 무변경)면 "N/A - 추가만".

### 6. 여러 방안이 있는 경우

설계 방안이 2개 이상이면 반드시 사람에게 선택을 요청한다.

### 6-1. Best-of-4 설계 (설계 게이트 대상만)

설계 게이트 대상이면 단일 초안 대신 **관점이 다른 4안을 병렬 생성 후 합성**한다.
게이트 비대상(내부 유틸, 리팩터링 등)은 이 절차를 생략하고 단일 설계로 진행한다.
**사전 승인 패턴에 완전히 부합하는 변경도 단일 설계로 진행한다** (best-of-4와
Devil's Advocate 생략 — 반복 검증된 패턴에 초안 팬아웃 비용을 쓰지 않는다.
가정 대장·정합 셀프체크·게이트 판정 기록은 유지 — 내력벽은 LOCK·뮤테이션·독립
리뷰다. 패턴 경계를 벗어나는 순간 일반 게이트 + best-of-4로 승격).

- 렌즈 초안 3개: 서로 다른 관점의 fresh-context 서브에이전트가 각각 작성 (저비용 모델)
  1. **minimal-first**: 최소 변경, 기존 자산 최대 재활용
  2. **risk-first**: 실패 모드·롤백·동시성·마이그레이션 안전 최우선
  3. **evolution-first**: 향후 확장 시 재작업 최소화 (단, YAGNI 위반 금지)
- **deep 초안 1개** (상위 모델, 렌즈 제약 없음, **조건부**): 문제 전체를 한 번에
  쥐고 가장 깊은 설계를 시도한다 — 데이터 모델 경계, 정규화, 추상화 수준 같은
  비분해적 판단이 핵심인 초안. 렌즈 3안은 넓이를, 이 초안은 judge가 고를 수 있는
  **깊이의 상한**을 올린다.
  생성 조건 (하나라도 해당): 신규 테이블 간 관계 설계 / 기존 테이블 스키마 변경 /
  트랜잭션 경계 설계 / 신규 도메인 개념 도입. **순수 additive 단순 CRUD**(관계 없는
  테이블 1개 + 표준 엔드포인트)는 비분해적 판단이 없으므로 렌즈 3안만으로 진행하고,
  생략 사유를 산출물 초안 표에 1줄 기록한다 (토큰 티어링 — 깊이가 필요 없는 곳에
  깊이 비용을 쓰지 않는다).
- judge(메인 컨텍스트, 상위 모델): 4안을 **고정 rubric으로 채점** 후 승자 기반으로
  합성하되, 탈락안의 좋은 부분은 이식한다. 채점표와 채택/기각 근거를 산출물에 남긴다.

  Judge rubric (안별로 각 항목 1~5점 + 근거 1줄, 총점이 아니라 항목별 비교로 판단):
  | 항목 | 기준 |
  |------|------|
  | 요구사항 커버리지 | 1단계 명세의 기능·제약을 빠짐없이 다루는가 |
  | 횡단 정합 | API↔스키마↔에러 정책↔트랜잭션 경계가 서로 맞는가 |
  | 되돌리기 비용 | 잘못됐을 때 롤백 난이도 (마이그레이션, 공개 인터페이스) |
  | 컨벤션 준수 | 기존 base/패턴 재활용, 레이어 규칙 |
  | 단순성 | 요구에 없는 추상화·유연성이 없는가 (YAGNI) |
- **컨텍스트 규약**: 초안 에이전트 입력은 0~2단계 산출물 파일 경로(1단계 요구사항
  명세 포함 — 설계가 요구사항을 직접 봐야 전달 손실이 없다) + **§0-2 결과(선택된
  접근 + 파생 요구사항 R-D# — 초안은 접근을 다시 고르지 않는다)** +
  `03-design-output.md` 의 템플릿뿐이다 (대화 이력 전달 금지). 출력은 템플릿 형식,
  표는 행당 1줄.

### 6-2. 가정 대장 (Assumption Ledger) — 필수

요구사항이 명시하지 않아 **에이전트가 스스로 정한 것**은 발생 즉시 전부 기록한다.
사람과 AI의 사고방식 차이로 생기는 사고는 대부분 여기서 시작된다.

각 항목: 무엇을 정했는지 / 가능한 다른 해석 / 이 해석을 고른 이유.
빈 대장은 "가정 없음"이 아니라 기록 누락으로 간주한다 — 없으면 "없음"을 근거와 함께 명시.

### 6-3. Devil's Advocate (설계 게이트 대상만 — 사전 승인 패턴 적용 시 생략)

사람 승인 요청 직전, **설계에 관여하지 않은 fresh-context 에이전트**에게 설계 문서만 주고
"사람이 놓치기 쉬운 위험"을 뽑게 한다. 출력은 위험 **최대 3개** × 각 2줄(위험/결과) —
실질 위험이 적으면 적게 내고 그 이유를 1줄 남긴다 (쿼터 채우기용 항목 금지).
결과는 게이트 브리핑에 그대로 첨부한다 — 설계자가 요약·완화하지 않는다.

### 7. 비판적 검토 (설계 게이트 대상)

설계 게이트 대상인 결정(되돌리기 어려운 것: DB 스키마, API 인터페이스, 아키텍처 패턴, 의존성)에 대해:

- 사람이 방향을 지시했더라도 추가 고려사항과 대안을 검토한다
- 더 나은 방안이 있으면 트레이드오프와 함께 사람에게 논의를 제안한다
- 비즈니스 흐름과 일정이 우선일 수 있으므로 강제하지 않는다
- 선택하지 않은 대안은 근거와 함께 결정 로그에 기록한다

### 8. 정합 셀프체크 (산출물 확정 전, 필수)

설계 문서만 보고 엔드포인트마다 경로를 시뮬레이션한다:
**요청 스키마 → 검증 → service 호출 → repo/트랜잭션 → 응답/에러**.
설계에 백그라운드 작업이 포함되면 비동기 경로도 같은 방식으로 시뮬레이션한다:
**enqueue → worker 처리 → 실패/재시도 → 최종 실패 처리**.

각 경로에서 표 사이 모순을 잡는다:
- 에러 정책 표에 없는 예외를 service가 raise하는가 (또는 그 반대)
- 비즈니스 규칙 표의 "위반 시" 예외가 에러 정책 표에 있는가, 규칙이 통과하는 경로가 엔드포인트에 있는가
- 응답 스키마에 있는 필드가 DB 설계에 없는가
- 상태코드 표와 에러 정책 표가 어긋나는가
- 트랜잭션 경계가 필요한 다중 쓰기가 명시돼 있는가

설계가 **기존 코드를 참조하는 항목**(재활용할 base 메서드, 기존 테이블·컬럼,
라우터 prefix, 기존 예외 클래스)은 기억으로 판정하지 않는다 — 해당 파일을 직접
열어(grep/read) 실재를 확인한다. 모델이 못 보는 오류도 파일은 드러낸다.

발견한 모순은 수정 후 산출물의 "셀프체크" 섹션에 "N개 발견·수정" 또는 "모순 없음"으로 기록한다.

### 8-1. 분기 완전성 (Gap B — 독립 finder, 조건부 필수)

§8이 표 사이 모순(쓰인 것끼리)을 잡는다면, 이건 **안 명명된 분기**를 찾는다 —
비즈니스 규칙·상태·에러 표가 다루지 않은 상태/경로. 안 명명된 분기는 4단계 테스트로
파생되지 않고(명명된 규칙에서만 파생), 뮤테이션도 못 잡고(테스트에 있는 것만 반전),
6단계 커버리지도 못 본다(코드에도 없으니) → 조용히 틀린 채 배포된다. 이 결함을
stage 7 코드 리뷰에서 잡으면 테스트가 이미 LOCK이라 재개방(override+사람)이 필요해
비싸다. **LOCK 전 여기서 잡아 규칙으로 착지시키면 싸게 테스트에 묶인다.**

**독립 필수**: 설계자 본인은 자기가 안 적은 분기에 눈멀었다(§8 셀프체크는 설계자
자신이 돈다). **설계에 관여하지 않은 fresh-context finder**(`branch-completeness-finder`)가
실행한다. verdict는 내지 않는다 — 게이트가 아니라 후보 분기를 설계에 먹이는 역할.
헛분기(false positive)는 사람 설계 게이트 + 4단계 LOCK 검수("설계에 없는 기능 테스트
금지")가 거르므로 **coverage-first**(확신 없어도 다 보고)로 돈다.

**컨텍스트 규약 (입력)**: finder에 주입할 것 = **1단계 요구사항 명세** + **3단계 설계
문서**(비즈니스 규칙·상태·에러 표 + §0-2 접근 결정) + 이 절의 taxonomy뿐. **대화 이력
금지**(독립성 훼손). 요구사항 명세를 반드시 함께 준다 — 설계 문서만 주면 *설계 내부*
완전성(명명된 상태끼리)만 보고, *요구가 함의하는데 설계가 안 만든* 분기는 못 잡는다.
두 입력의 대조가 미명명 분기를 드러낸다. 출력은 아래 taxonomy 형식, 표는 행당 1줄.

**발동 게이트 (하나라도 — 아니면 "분기공간 없음 — N/A" 1줄로 생략)**:
- 비즈니스 규칙 2개 이상, 또는 규칙 중 상태/status 조건이 하나라도 있음
- §0-2에서 로직 접근(동시성/상태모델/집계/권한모델)을 결정함
- 상태 전이가 있는 엔티티를 다룸

(순수 CRUD — 규칙 "없음" + §0-2 "해당 없음" + 상태 없음 — 은 생략)

**taxonomy (고정 6유형 순회 — 완전성을 모델 천재성이 아니라 구조로 보장. 뮤테이션
연산자 5종과 같은 처방)**: 각 유형마다 "해당 지점 있나 → 명시됐나, 없으면 `N/A - 사유` 1줄":

1. **상태 × 동작** — 각 상태(특히 비해피: 취소됨·만료·잠김·처리중)에서 각 동작 결과가
   명시됐나. 빈 셀 = 안 적은 분기 (예: "환불중 주문 취소하면?")
2. **else/부정 arm** — 각 규칙 조건의 반대편이 명시됐나 ("X면 허용" → not-X면?)
3. **경계·영역** — 임계·수량 규칙의 0/경계/초과/미만이 규칙에 있나 (재고 0, 상한 도달)
4. **빈/없음/초기** — 0건 조회, 첫 레코드, null 옵셔널, FK 대상 부재
5. **동시·중복·순서** — §0-2 정합성 전략의 분기가 다 명시됐나 (동시요청·중복제출·재시도)
6. **실패·부분실패** — 외부호출 타임아웃, 다단계 쓰기 중간 실패, 재시도 소진 최종상태

**security 카브아웃**: authz/IDOR/접근권한 분기는 다루지 않는다 — stage 7 security
렌즈 + `cto-reviewer`의 authz 프로브가 임자다(중복 방지 + 상위 모델 보안분석 거부·약화
회피 — `adversarial-reviewer`의 security 카브아웃과 동일 원칙). "소유자별 다른
데이터"의 *무슨 데이터*(로직)는 보되 *접근 허용 여부*(보안)는 제외.

**모델 (마스터가 spawn 때 결정, 에이전트 정의에 핀 없음)**: 기본 **sonnet** —
taxonomy가 완전성을 구조로 나르므로(뮤테이션이 sonnet인 것과 동일 원리). 다음 중
하나면 **fable 승급** — 판단이 아니라 설계가 이미 낸 필드를 읽어 결정:
게이트 브리핑 "되돌리기 사실상 불가" 또는 파괴적 변경 / 결제·PII 도메인 / §0-2
트랜잭션 경계·정합성 전략.

발견한 각 분기는 비즈니스 규칙 표에 행으로 추가하거나 `R-B#` 파생 요구사항으로 승격한다
— 4단계 커버리지가 순회하도록. 미발동이면 산출물에 "분기공간 없음 — N/A" 1줄.

### 9. 설계 변경 (개발 중 요구사항 추가/변경 — 델타 재설계)

승인된 설계가 있는 상태에서 요구사항이 바뀌면 3단계를 통째로 재실행하지 않는다.
절차 (순서 고정):

1. **파급 판정 (독립, 필수 — 변경 당사자 판정 금지)**: fresh-context 비평가(상위 모델)에게
   기존 설계 문서 + 변경 요구만 주고, **기존 설계 항목 중 이 변경이 무효화하거나
   수정을 요구하는 것의 목록**을 뽑게 한다 (테이블/스키마/엔드포인트/에러 정책/
   트랜잭션 경계/가정 대장 항목 단위). 코드가 이미 있으면 grep으로 실제 확인.
   **판정은 보수 편향**: 등급이 모호하면 한 단계 위로 (교차 없음↔부분이 애매하면
   부분, 부분↔근간이 애매하면 근간). 판정 실패의 비용이 비대칭이다 — 과대판정은
   토큰 낭비, 과소판정은 검증 안 된 설계가 게이트를 우회한다.
2. **판정에 따른 승격**:

   | 파급 판정 결과 | 절차 |
   |---------------|------|
   | 교차 없음 (순수 추가) | amendment만 — 변경 내역 섹션 + 영향 맵 델타 + 가정 대장 갱신 |
   | 기존 항목 N개 수정 필요 | 그 항목들을 **포함한** 부분 재설계 + §8 셀프체크 전체 재실행 |
   | 설계 근간 변경 (데이터모델 경계, 트랜잭션 구조, 인증 흐름) | **3단계 풀 재실행으로 승격** (best-of-4 포함) |

3. **게이트 재승인**: 변경이 새 게이트 조건을 발생시키면 (새 테이블, 새 엔드포인트,
   파괴적 변경 등) 재승인 필수. 기존 승인 범위 안이면 결정 로그 기록만.
4. **LOCK 교차**: 변경이 LOCK된 테스트의 계약과 충돌하면 사람 승인 후
   `TEST_LOCK_OVERRIDE=1`로 4단계 재개방 (기존 override 규칙 그대로).
5. amendment는 기존 설계 문서에 "## 변경 내역 (YYYY-MM-DD)" 섹션으로 append —
   원본을 고쳐쓰지 않는다 (승인 이력 보존). 결정 로그에 파급 판정 결과를 기록한다.
6. **누적 상한**: 같은 기능에서 amendment가 2회 쌓인 뒤 세 번째 변경 요구가 오면
   파급 판정 없이 **풀 재설계로 자동 승격**한다 — amendment 위에 amendment가 쌓이면
   각 변경은 국소적으로 정합해도 전체 설계가 조각나며, 그 드리프트는 파급 판정이
   못 본다 (판정 입력이 이미 조각난 문서이므로).

§8 셀프체크는 어떤 경로든 amendment 후 다시 실행한다 (경로 시뮬레이션은 인라인이라 싸다).

### 실패 시
- 기존 코드와 충돌 → 사람에게 보고
- 설계 방안 2개 이상 → 사람에게 선택 요청
- 누락 발견 → 사람에게 확인

## Rules

- 기존 패턴을 따른다. `.agents/context/codebase-conventions.md` 참조.
- 요구사항에 없는 엔드포인트나 필드를 임의로 추가하지 않는다.
- 설계 방안이 여러 개이면 반드시 사람에게 선택을 요청한다.
- 누락을 발견하면 사람에게 확인한다.
- 설계 게이트 조건에 해당하면 사람의 승인 없이 다음 단계로 진행하지 않는다.
- **설계 근거 필수**: 모든 설계 결정에 "왜 이 방안인지" 근거를 명시한다. 사람이 읽고 이해할 수 있어야 한다.
- **비판적 검토**: 되돌리기 어려운 결정은 대안을 검토하고, 더 나은 방안이 있으면 사람에게 논의를 제안한다.
- **가정 대장 필수**: 요구사항에 없는 걸 스스로 정했으면 전부 기록한다. 게이트 승인은 가정 대장을 포함한 상태에서만 요청한다.
- **게이트 브리핑 필수 (게이트 대상)**: 사람이 코드를 몰라도 위험과 되돌리기 비용을 판단할 수 있게 쓴다. Devil's Advocate 출력은 원문 그대로 첨부한다.
- **결정 로그**: 이 단계 완료 시 설계 결정, 근거, 검토한 대안, 가정 대장, 사람 승인 여부를 결정 로그에 append한다.
