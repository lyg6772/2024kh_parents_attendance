# 4단계: 테스트 코드 생성 (Test-First)

## Role

설계 문서를 바탕으로 테스트 코드를 먼저 작성한다.

**이 단계는 설계 게이트 대상인 경우 3단계 설계가 사람의 승인을 받은 후에만 실행한다.**

## Input

- 3단계 산출물: 설계 문서 (게이트 대상이면 사람 승인 완료)
- 1단계 산출물: 요구사항 명세 (artifacts 경로 — 요구사항→테스트 추적용.
  설계가 요구사항을 누락했으면 여기서 드러난다 → 3단계 반환)
- 0단계 산출물: 코드베이스 컨텍스트 + 재활용 목록

## Process

### 1. 테스트 레이어 배정

레이어는 **축**으로 정의된다 — 이름과 도구는 스택마다 다르므로 커널이 갖지 않는다.
각 축이 이 레포에서 무엇인지 판정하고, 그 판정을 산출물의 **레이어 배정 표**에 남긴다.

| 축 | 판별 질문 | 이름 예 (스택별 — 그대로 쓰지 말 것) |
|---|---|---|
| **격리** | 외부 의존 없이 로직만 도는가 | 웹 백엔드: unit(repository·schema) / 프론트: 컴포넌트 / CLI: 함수 단위 / 라이브러리: 공개 함수 |
| **결합** | 여러 구성요소가 실제 의존(DB·파일시스템)과 함께 도는가 | 웹 백엔드: integration(엔드포인트+DB) / 프론트: 상호작용 / CLI: 파일시스템 왕복 |
| **계약** | 외부에 노출한 인터페이스의 **형태**를 고정하는가 | 웹 백엔드: API 스키마·OpenAPI / CLI: 인자·종료코드·stdout / 라이브러리: 공개 타입·시그니처 / 프론트: 소비자측이라 보통 N/A |
| **전체 경로** | 사용자가 실제로 하는 것을 끝까지 도는가 | 웹 백엔드: e2e HTTP 시나리오 / 프론트: 브라우저(playwright) / CLI: 프로세스 실행 / 라이브러리: 보통 N/A |

**예시 열은 예시다.** 그 단어가 이 레포에 없으면 축이 없는 것이 아니라 **이름이 다른
것이다** — 이 레포에서 그 축이 무엇인지 판정한다. (레포가 레이어를 선언하는 노브는
아직 없다 — 판정은 매번 이 단계가 하고 산출물에 남긴다.)

**설계가 함의하는 축은 사유 없이 비울 수 없다.** 어느 축이 대상인지는 §3-2와 같은
기준으로 정한다 — 설계 표가 함의하면 대상이다 (API 표 → 계약, 사용자 플로우 →
전체 경로). 함의하는데 미작성이면 **사유가 필수**이고, 함의하지 않으면 "—" 한
글자로 끝낸다. 사유 없이 비어 있는 함의 축은 조용한 누락이다.

**이 표를 읽는 기계 오라클은 없다** (`장치: 없음`) — 4단계 LOCK 전 검수(§4)와
7단계 verifier가 사람·모델 판단으로 본다. 표는 누락을 **보이게** 만들 뿐 막지 않는다.

작성 순서: **격리 → 결합**이 기본. 마이그레이션/인프라 변경은 결합 우선. 순수
로직은 격리만으로 충분할 수 있다.

**작성 절 위치**: 격리는 §2, 결합은 §3, **계약은 §3-2**(설계 함의 시 파생),
**전체 경로는 아래 문단**. 네 축 모두 이 단계 안에서 작성한다 — 절이 따로 없는
축이 나중 단계로 미뤄지는 것이 아니다.

**전체 경로 축에 자산이 있으면 그것도 이 단계의 산출물이다** — 6단계의 e2e
실기동(수동 1회, 회귀 자산으로 남지 않음)과 별개다. 레포에 e2e 스펙(playwright 등)이
있으면 여기서 작성한다.

**단 LOCK 강제 범위가 층마다 다르다.** 커밋 시점 훅(pre-commit `test-lock` →
`test_lock_check.sh`)과 CI 락윈도 감사(`scripts/audit/20-test-lock.sh`)는 `TESTS_DIR`
접두사로 판정하고, **편집 시점 가드(`test_lock_guard.sh`)는 `tests/` 하드코딩**이라
`TESTS_DIR` 이 다르면 그 층은 무력이다 (그 스크립트가 KNOWN LIMIT 으로 명시한다).

따라서 e2e 자산이 `TESTS_DIR` 밖(`e2e/` 등)에 있으면 **어느 층도 보지 않는다** —
배정 표에 그 사실을 적고, 그 자산은 규범으로만 보호된다 (잠겼다고 적지 않는다:
강제되지 않는 LOCK 선언은 검증되지 않은 완료다).

### 2. 격리 축 작성

설계 문서의 각 구성요소에 대해 외부 의존 없이 로직을 검증한다:

- 기존 픽스처 재활용, 도메인 특화 메서드
- 유효성 검증이 복잡한 경우 그 규칙 자체

### 3. 결합 축 작성

설계 문서의 각 진입점(엔드포인트·명령·핸들러)에 대해 실제 의존과 함께 검증한다:

- 정상 케이스 (해피 패스)
- 에러 케이스 (설계에 정의된 에러 상황)
- 유효성 검증 실패 케이스

### 3-1. 입력 경계 파생 (필수)

설계에 정의된 규칙에서 테스트 입력을 **기계적으로 파생**한다 — 이는 설계의
파생이지 "설계에 없는 케이스"가 아니다:

- 스키마 표의 각 검증 규칙 → 경계값 3종 (정확히 경계 / 초과 / 미만)
- 비즈니스 규칙 표의 각 입력 조건 → 충족 케이스 + 위반 케이스 (기대 예외까지)
- 해당되는 곳에 이상 입력: null/누락, 빈 값, 중복, 타입 불일치, unicode/특수문자
  (문자열 필드), 순서 의존성(순서가 결과에 영향 있으면)

### 3-2. 계약·중복·멱등 파생 (설계 함의 시)

§3-1이 입력을 파생하듯, 아래는 설계 표가 **함의할 때** 파생한다 (함의 없으면 생략):

- **계약 (API 표 있으면)**: 응답 본문이 설계 Response 스키마와 일치 / HTTP status가
  API 표와 일치 / 에러 응답 형식이 에러 정책 표와 일치. **계약 축이 이 레포에 있으면
  거기에**, 없으면 결합 축에서 어서션한다 (§1 배정 표에 어느 쪽인지 적는다).
- **멱등 (설계가 멱등키·재시도 정하면)**: 동일 요청 반복 시 결과 동일.
- **충돌 (유니크 제약·멱등 설계 있으면)**: 중복 생성 시 409 등 설계된 충돌 응답.
- **중복 규칙 (dedup — anti-bloat)**: 공통 인증 미들웨어는 **한 번만** 테스트하고
  재사용한다. API별 인가 정책·비즈니스 규칙은 **정책이 다를 때만** 각각 테스트한다.
  엔드포인트마다 공유 동작을 재테스트하지 않는다 (커버리지가 아니라 중복).

### 4. LOCK 전 독립 검수 (필수)

작성을 마치면 확정 전에 **테스트 작성에 관여하지 않은 fresh-context 에이전트(상위 모델)**가
설계 문서 대비 테스트를 검수한다. 테스트는 LOCK되면 파이프라인 전체를 구속하는 계약이므로
잘못 쓰인 채 잠기면 가장 비싸다.

검수 관점: 설계의 기능·에러 정책·비즈니스 규칙 커버리지 누락 / 1단계 요구사항
커버리지 표의 정확성 / 경계·계약·중복·멱등 파생(§3-1, §3-2) 누락 / 설계와 다른
스펙을 검증하는 테스트 / 실질을 검증하지 않는 약한 assertion / 설계에 없는 기능을
검증하는 임의 케이스.

**테스트 taxonomy 루브릭**: `.agents/context/test-taxonomy.md`를 커버리지 채점표로
순회한다. 항목을 기계적으로 채우는 폼이 아니라 — **각 항목의 적용성은 설계 함의로
판단**한다: 설계·비즈니스 규칙·에러 정책·§0-2 파생 요구사항이 함의하면 커버/미커버로
채점하고, 함의하지 않으면 `N/A — 사유 1줄`로 내린다 (concurrency/property/perf 등
조건부 항목이 특히 여기서 걸러진다). 설계가 요구하는데 빠진 것만 지적한다.
검수 지적은 이 단계 안에서 반영 후 확정한다 (아직 LOCK 전이므로 자유 수정 가능).

### 4-1. 뮤테이션 검증 (LOCK 직전, 필수)

검수 반영 후 LOCK 전에, 테스트가 진짜 그물인지 **실행으로** 확인한다.
독립 fresh-context 에이전트(저비용 모델 — 판정은 모델이 아니라 테스트 러너 실행이
하므로 티어링 원칙상 sonnet으로 충분)에게 설계 문서 + 테스트 코드를 주고:

> "모든 테스트를 통과하면서 설계 스펙을 위반하는 구현을 작성하라.
> 허점을 발견해야 이 테스트의 완성도가 올라간다."

아무 허점이나 찾되, `.agents/context/test-taxonomy.md` §7의 **연산자 5종을
체계적으로 시도**한다 (아무거나 하나만 뚫려도 테스트 보강 대상): Off-by-One
(경계값 ±1) / Missing Validation (검증 한 줄 제거) / Wrong Branch (조건 분기 반전) /
Incorrect Order (처리 순서 변경) / Duplicate Processing (중복 실행). 설계에 해당
연산자가 물릴 지점이 없으면 그 연산자는 건너뛰고 사유를 산출물에 1줄 남긴다.

- 에이전트가 **성공** (테스트 그린 + 스펙 위반 구현 존재) → 그 위반 경로를 잡는
  테스트를 추가하고 다시 시도한다. 성공 못 할 때까지 반복 (최대 2라운드,
  이후에도 뚫리면 사람에게 보고).
- 에이전트가 **실패** (뚫지 못함) → 시도한 공격 경로 목록을 산출물에 기록하고 LOCK.
- 뮤테이션용 임시 구현은 LOCK 전에 전부 폐기한다 (`git restore`로 테스트 외 파일
  원복 + untracked 파일 삭제, 커밋 금지) — 5단계는 백지에서 시작.

판정 기준이 추론이 아니라 **테스트 실행 결과**이므로, 테스트 작성자와 같은 모델
계열이라도 맹점이 실행으로 드러난다.

### 4-2. 결정성 게이트 (LOCK 직전, 필수)

flaky 테스트는 곧 잘못 잠긴 테스트다 — LOCK되면 6단계에서 무작위 레드를 내며 파이프라인
전체를 오염시키는데, 그 원인(순서 의존·시간·전역 상태)은 구현이 아니라 테스트에 있다.
LOCK 전에 새로 추가한 테스트를 **2회 실행**한다 (러너가 순서 무작위화를 지원하면
두 번을 다른 순서로 — 예: `pytest-randomly` 설치 시 시드 다르게; 커맨드는 conventions 참조).

- 두 번 다 동일하게 그린 → 통과, LOCK 진행.
- 결과가 갈리거나 순서에 따라 실패 → **flaky. 원인을 제거한 뒤**(고정 시드, 격리,
  명시적 정렬) 다시 2회. 구현으로 넘기지 않는다 — 테스트 결함이다.
- 산출물에 `결정성: 2회 그린 / flaky N개 수정 후 통과`를 기록한다.

### 5. 테스트 확정 및 보호

검수(§4)와 뮤테이션 검증(§4-1)이 끝나면 테스트 코드를 확정하고 LOCK 마커를 생성해 **커밋한다**:
`.agents/context/locks/<feature-name>.lock` — **1행: 전체 브랜치 이름**
(예: `feat/user-auth` — 훅이 이 행으로 현재 브랜치와 매칭하며, 접두사를 뺀
`user-auth`도 허용), 2행: LOCK 시각, 3행~: 테스트 파일 목록.

마커를 커밋하는 이유: 브랜치와 함께 이동해 **CI(process-audit)가 서버측에서
LOCK 윈도우를 감사**할 수 있다 — 마커 생성~삭제 커밋 사이에 `tests/`가 변경됐는데
결정 로그에 `override 사용:` 기록이 없으면 PR이 레드. feat 브랜치에 lock 커밋이
아예 없어도 레드 (파이프라인 미준수 또는 히스토리 재작성 은폐). 로컬 훅은
`--no-verify`로 우회 가능하지만 이 백스톱은 히스토리 재작성 없이는 못 지운다 —
그 마지막 구멍은 branch protection(force-push 금지 + 사람 PR 승인)이 막는다.

pre-commit `test-lock` 훅은 **현재 브랜치와 일치하는** 마커 존재 시 `tests/` 변경
커밋을 차단한다. 다른 브랜치의 마커는 차단하지 않는다 (동시 개발 안전).

**5단계(구현)~7단계(리뷰) 동안 테스트를 수정할 수 없다.** 7단계 리뷰를 통과하면
LOCK 마커를 삭제하고 보호가 해제된다. (사람이 승인한 4단계 재수정 시에는 사람이
`sh scripts/unlock_tests.sh <feature>`를 실행한 뒤 — /dev/tty 확인, 에이전트 단독
불가 — `TEST_LOCK_OVERRIDE=1`로 커밋. 승인 근거를 결정 로그에 기록.)

## Rules

- 기존 테스트 파일의 스타일을 따른다.
- 기존 픽스처를 재활용한다. 새 픽스처가 필요하면 레포 테스트 규약의 공용 픽스처 위치에 추가한다 (예: pytest면 `conftest.py`).
- 설계에 없는 **기능**을 테스트하지 않는다. 단, 설계에 정의된 검증 규칙·비즈니스
  규칙의 경계값·이상 입력 파생(§3-1)과 설계가 함의하는 계약·멱등·충돌 파생(§3-2)은
  임의 추가가 아니라 의무다. 조건부 항목(concurrency/property/perf)은 설계 함의가
  있을 때만 — 없으면 taxonomy 검수에서 N/A로 처리한다 (일괄 추가 금지, bloat 방지).
- 이 단계에서는 테스트를 자유롭게 추가/수정할 수 있다. 설계를 정확히 반영하도록 충분히 다듬는다.
- **보호 범위: 4단계 완료 ~ 7단계 통과.** 구현/검증/리뷰·리팩토링 중에는 에러 통과를 위해 테스트를 임의로 수정하지 않는다.
- **7단계(독립 리뷰) 통과 시 보호 해제 + LOCK 마커 삭제.** 이후에는 필요 시 수정 가능하다.
- 사람이 명시적으로 수정을 지시한 경우는 보호 중에도 예외.
- 테스트가 객관적으로 잘못된 경우(설계 반영 오류 등), 사람에게 보고하고 승인받아 수정한다.
- 테스트가 실패하면 구현이 틀린 것이다. 테스트를 고치지 않는다.
- **결정 로그**: 이 단계 완료 시 테스트 전략(작성 순서, 이유), 테스트 파일 목록, LOCK 시작을 결정 로그에 append한다.
